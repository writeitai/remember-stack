# OpenRouter provider rotation + 429 policy (chat path)

Binding design for D127. Analysis:
`plan/analysis/openrouter_inference_capacity_20260916.md`.
Status: accepted and implemented.

## Problem

Before ordered rotation, the chat seat pinned providers with `allow_fallbacks: false`: when the
routed provider overloads, the adapter retry and the work-ledger retries all hit the same
engine, converting transient 429s into dead letters (R14: 45/997 from DeepInfra 429s).
Embeddings already declared an ordered shortlist with OpenRouter-side fallbacks;
neither path rotated client-side on overload.

## Decision

Bring the chat path to the embedding pattern, with three additions: overload-triggered
rotation, a split throttle budget, and per-call host recording.

## Contracts

### 1. Ordered chat shortlist with fallbacks

- New setting `chat_provider_order: list[str] | None = None` (same comma-separated-slug
  parsing as `embedding_provider_order`, new validator entry reusing
  `_parse_provider_name_list`). Env:
  `REMEMBERSTACK_OPENROUTER_CHAT_PROVIDER_ORDER`. Sent as
  `{"order": [...], "allow_fallbacks": true}`.
- Default is `None`: a hardcoded provider list would break every other model on the
  shared adapter. The surveyed order DeepInfra → Relace → Wafer is the recommended
  **deployment/env-level** configuration for GLM (documented in the ops runbook, not in
  code). InferenceNet stays out of the recommendation until its uptime stabilizes;
  GMICloud/StreamLake stay out while they retain prompts.
- `chat_provider_only` is a hard allowlist with no marketplace escape. Alone it
  disables fallback. It can be combined with `chat_provider_order` when the order
  names exactly the same unique slugs: fallback then stays within that approved
  set. Setting neither keeps automatic routing. For example, an owner who accepts
  standard pricing after Flex exhaustion can approve and order
  `openai/flex,openai` in both settings, without changing the requested model.
- Rotation operates on the effective slug list from **either** setting: on overload the
  adapter advances past the failed slug. A single-slug `only` has nowhere to advance, so
  it keeps today's behavior (throttle budget, then the typed error).

### 2. Rotate on overload, not just wait

- On 429 with an upstream-overload signal (`provider_error_code: engine_overloaded` or
  equivalent), the adapter advances to the next pinned slug instead of only sleeping and
  re-posting to the same routing. Retry-After is still honored as a floor.
- Rotation is bounded (at most one attempt per slug per logical call) so the existing
  "one provider call per logical call" accounting invariant bends in a recorded way, never
  silently: **every attempt emits its own `GenerationRecord` span** — intermediate 429s
  with `outcome = transport_error` (exactly how R14's 193 failures are visible today),
  the terminal attempt with its outcome plus serving host (see 4).

### 3. Throttle budget separate from work attempts

- Capacity rejections draw from a dedicated throttle budget (exponential backoff with jitter,
  Retry-After honor) and do **not** consume the work ledger's attempt budget. A hot pool
  may delay work within that bounded budget. The explicit OpenAI Flex
  "processing is temporarily unavailable" rejection is also recognized inside
  an HTTP-200 error envelope with a transient gateway code (429, 500, 502, 503,
  504, 529) or absent code, provided the response
  has neither `choices` nor `usage`. OpenRouter may assign an ID before this
  uncharged admission rejection; that ID alone does not prevent its bounded
  retry. An authentication/validation code excludes the classification.
- A response carrying choices or usage is never regenerated by this capacity
  path, including empty or malformed fields. An ID-bearing generic error is
  not assumed uncharged. The hard provider allowlist stays in force on every
  retry. Standard-price fallback requires that endpoint in the explicit approved
  routing policy; Flex exhaustion alone never widens the allowlist. Actual usage
  is recorded at the serving endpoint's rate, not an assumed Flex rate.
- The explicit transient envelope `error.metadata.error_type = provider_unavailable`
  is another recognized unbilled rejection, subject to the same HTTP/error-code
  checks and strict absence of both `choices` and `usage`. An allocated ID is
  allowed for this specific rejection. It uses the existing throttle budget,
  approved provider set and transport-event recording, without fabricating usage
  or first attempting to reconcile a nonexistent completed generation. Generic
  ID-bearing errors still require accounting recovery. This distinction follows
  [OpenRouter's failed-attempt billing contract](https://openrouter.ai/pricing)
  (retrieved2026-11-09); the adapter does not request separately billable auxiliary
  services. Incident evidence and alternatives are in the
  [unavailability analysis](../analysis/openrouter_provider_unavailable_20261109.md).
- Successful responses require usable token/cost accounting. If inline
  accounting is unusable, poll only the existing generation's metadata with
  the bounded 0/1/2/3/5-second waits. Exhaustion remains a nonretryable
  `ProviderAccountingError`. Its durable worker error retains the bounded
  generation ID, original inline reason, lookup count and final metadata HTTP
  status, without copying provider messages or completion text. Unknown cost
  remains unknown. When the existing private invalid-completion capture is
  explicitly enabled, retain the original unaccounted response there with
  mode 0600, never a fabricated usage record. This is diagnostic customer data,
  disabled by default, and does not authorize automatic paid replay. See the
  [accounting-failure analysis](../analysis/openrouter-accounting-failure-525-20261106.md)
  for the November 6 evidence and upstream contracts.
- A success-status reply whose body is not a JSON object is a broken provider
  reply. It is neither a capacity rejection nor an invalid model answer.
  Examples are an empty body, whitespace only, non-JSON text such as an HTML
  page, a cut-off object, bytes that are not valid text, or a JSON array,
  string, number, boolean or null. Every `OpenRouterModelProvider` POST path
  (chat with or without rotation, and embeddings) reads the body through one
  shared check. That check raises the ordinary typed `OpenRouterProviderError`
  after the capacity checks above have already declined the reply. On the
  rotation path the error carries the targeted slug. The image-description
  converter (`adapters/converters/image_ocr_description.py`) also POSTs to
  OpenRouter but does not use this check. It has its own equivalent guard: a
  success reply that is not a JSON object becomes a typed `ProviderCallError`
  with no usage events.
  - **Safe diagnostics.** The message holds only the endpoint, the status, the
    body size in bytes, a body class, and the JSON decoder's fixed reason and
    character offset. It never includes body text, headers or credentials,
    because a partial reply can repeat user content. The error is raised with
    no decoder exception attached as cause or context, because that exception
    holds the raw body and would print its own message in a traceback. This
    covers the message and the exception chain, not memory: the response
    object still exists in the callers' frames.
  - **Billing.** A success status does not prove the request was free. Usage
    stays unknown (`None`), never zero. The error is never classified as an
    unbilled rejection. The adapter does not retry it, rotate to another slug,
    or open a new retry budget. `generate()` records it once with
    `outcome = transport_error`. Callers handle it as an ordinary provider
    error under their existing policy: stages that fail closed leave any
    retry to the work ledger, and fail-open steps (such as E0 section
    summaries) continue without the answer.
  - **Not an invalid response.** For embeddings, an invalid-response error
    marks a chunk as poison (content that can never embed). A broken reply
    says nothing about the chunk, so it is treated as a provider outage.
  - **Unchanged.** Valid replies, including a valid object preceded by
    whitespace, decode as before.
  - See the
    [malformed-success analysis](../analysis/openrouter_malformed_success_body_20261113.md)
    for how this gap was found and what it does not explain.
- Exact settings on `OpenRouterSettings`, alongside the existing
  `_IN_FLIGHT_BUDGET_RETRIES` so operators can reason about worst-case latency (R14 showed
  ~13 s per failed call; the design must keep worst-case bounded and visible):
  - `chat_throttle_retries: int = 3` (env `REMEMBERSTACK_OPENROUTER_CHAT_THROTTLE_RETRIES`,
    dedicated 429 attempts per logical call, shared across slugs in the rotation).
  - `chat_upstream_overload_max_retry_after_s: float = 30.0` (env
    `REMEMBERSTACK_OPENROUTER_CHAT_UPSTREAM_OVERLOAD_MAX_RETRY_AFTER_S`, per-wait cap; an explicit
    Retry-After below the cap wins, anything above is clamped to the cap).

### 4. Record the serving host per call

- `GenerationRecord` gains the serving provider/host name; the recorder emits it as a
  `locomo.provider_host`-style attribute next to `locomo.run_tag`. Today's autopsy could
  name DeepInfra only because the error body said so; successes must record it too.
- Discovery mechanism, in order: (a) the response-body `provider` field when present on
  the chat completion; (b) the generation lookup by response id through the existing
  `fetch_generation` plumbing (returns `provider_name`); (c) fallback to the rotation
  slug the attempt targeted. The implementing PR verifies (a)/(b) against the live API
  and tests the fallback; if neither field exists, the fallback is the mechanism.
- Benchmark comparability rule (binding): rotating hosts during a call serving
  the **same pinned model + params + approved routing policy** does not change
  `readiness.model_bindings` (`EXPECTED_INGEST_MODEL_BINDINGS`),
  `surface_manifest_hash`, or `protocol_fingerprint`.
  `chat_provider_order`, the throttle settings, and the ZDR flag are **transport settings
  and are excluded from `_model_bindings()` in `profiles/selfhost.py`** — unlike
  `embedding_provider_order`, which is in bindings today, so an implementer copying that
  precedent without this exclusion would break the benchmark equality gate. The
  embedding allowlist (§5) is disclosed as `openrouter_embedding_provider_only`
  only when it is set, so bindings without it stay byte-identical. The
  implementing PR asserts all three fingerprints stable across serving hosts.
  A benchmark's configured execution policy and worker environment are separately
  fingerprinted: changing the approved endpoints or pricing policy requires a
  newly prepared run rather than rewriting an existing checkpoint's identity.

### 5. Zero-retention enforcement

A zero-data-retention (ZDR) endpoint is one whose host does not store prompts
or outputs after answering. OpenRouter filters candidate hosts, fallbacks
included, by two `provider` fields: `zdr: true` (ZDR endpoints only) and
`data_collection: "deny"` (no hosts that collect user data). Every OpenRouter
call that carries customer content can be held to both.

- Chat payloads always send `data_collection: deny` in the provider dict when
  any provider list or ZDR is configured.
- `zdr: bool = False` (env `REMEMBERSTACK_OPENROUTER_ZDR`): when true, every chat
  **and embedding** request's provider dict carries `zdr: true` and
  `data_collection: deny`, also when no provider list is configured (the dict
  is then exactly `{"data_collection": "deny", "zdr": true}`). Provider picks
  already exclude retaining hosts by default (see order above); the flag is the
  enforcement, not the pick. Because both fields filter fallbacks too, the
  retention guarantee does not depend on how OpenRouter treats `only` or
  `order` during failover.
- The request flags are necessary but not sufficient for strict zero
  retention. OpenRouter applies the account's (or the API key's guardrail's)
  Safety Retention policy on top of a request's `zdr: true`: endpoints that
  keep flagged content for safety review still count as ZDR unless the account
  or guardrail opts out of Safety Retention, and self-serve accounts allow it by
  default. A deployment that requires strict zero retention therefore also sets
  the OpenRouter account, or the guardrail on every API key it uses, to ZDR only
  with Safety Retention excluded, and verifies that setting before sending
  customer content. No request field can turn it off, so the engine cannot
  enforce it; it is an operator obligation, stated here and in the public docs.
- Embedding host allowlist, `embedding_provider_only: list[str] | None` (env
  `REMEMBERSTACK_OPENROUTER_EMBEDDING_PROVIDER_ONLY`, comma-separated or JSON
  slugs, parsed like `chat_provider_only`). It bounds price and hosts the way
  `embedding_provider_order` alone cannot: `order` is only a preference, and
  with `allow_fallbacks: true` OpenRouter may fail over to any host serving the
  model. Payloads (ZDR fields added when `zdr` is true):

  | Embedding settings | `provider` object |
  | --- | --- |
  | `only` with two or more hosts | `{"only": [...], "allow_fallbacks": true}`: OpenRouter picks among the listed hosts and fails over only within them |
  | `only` with one host | `{"only": [x], "allow_fallbacks": false}` |
  | `only` plus an `order` naming the same two or more hosts | `{"order": [...], "only": [...], "allow_fallbacks": true}`: tried in that order, never outside `only` |
  | `only` plus an `order` naming the same single host | `{"order": [x], "only": [x], "allow_fallbacks": false}` |
  | `order` alone | `{"order": [...], "allow_fallbacks": true}`: may leave the list |
  | single `embedding_provider` pin | `{"only": [x], "allow_fallbacks": false}`; an `order` wins over it, as before |
  | nothing, ZDR off | no `provider` object |

  Validation refuses contradictory routing at startup: `embedding_provider_only`
  with the single `embedding_provider` pin (two hard allowlists), an allowlist
  naming a host twice, and an `order` that does not name exactly the allowlist's
  hosts once. `allow_fallbacks` follows the allowlist's length, with or without
  an order: true for two or more hosts, false for one. A malformed allowlist (an
  empty JSON list, or a blank or non-string entry) is refused at startup rather
  than read as unset, so it can never silently re-open marketplace fallback.
  Unlike chat, the allowlist alone allows fallback within it,
  because an embedding batch pinned to one failing host would dead-letter the
  stage; chat gets the same in-set failover from its local rotation.
- The image-description converter posts pixels through its own client and
  settings, so it has its own flag, `ImageDescriptionSettings.zdr` (env
  `REMEMBERSTACK_IMAGE_DESCRIPTION_ZDR`). When true, every description attempt,
  including endpoint-rotation retries, adds `zdr: true` and
  `data_collection: deny`, with or without its `provider_only` list. The flag is
  a privacy filter on the same model and prompt, so it stays out of the
  converter's version fingerprint and never re-converts stored images (D56).
- Providers outside OpenRouter (Mistral OCR, TypeSafe SystemOne, the OpenAI
  Decisions backup, Vertex) are not governed by these flags; their retention
  is an account or contract setting of the deployment. Rationale and the
  OpenRouter documentation this relies on:
  [embedding ZDR analysis](../analysis/openrouter-embedding-zdr-20261124.md).

## Failure / recovery

- All pinned slugs overloaded: bounded waits, then the existing typed provider error
  surfaces and the work ledger retries later as today — no new unbounded loops.
- Rotation state is per logical call, never shared across workers: no cross-request
  coordination, no sticky state to go stale.
- Cost impact: BYOK 5% fee applies per OpenRouter's terms; usage accounting stays
  one-record-per-attempt so spend remains reconcilable (R14's 193 unaccounted failed calls
  stay visible as attempts, not gaps).

## Security / operational consequences

- Provider keys stay in GCP Secret Manager / GitHub Actions secrets and the OpenRouter
  dashboard (BYOK); secret **names** in `infra/`-style inventory only. No keys in repo,
  logs, or traces (the recorder never emits credentials; review must confirm the new host
  attribute carries no secret material).
- Operators get a 429-rate signal per host (the recorder attribute makes it queryable);
  alert on throttle rate, not only on dead letters.
- UMC picks this up via its pinned engine dependency bump; per-tenant key management is
  explicitly out of scope here (UMC productization follows).

## Alternatives (why not)

- Locomo-only routing: rejected — forks benchmark from product behavior.
- Model switching on throttle: rejected — breaks comparability silently.
- Pure BYOK with no rotation: accepted as the ops complement, insufficient alone (one
  key's engine can still overload).
- First-party Z.AI adapter: deferred follow-up, not a substitute.

## Implementation-facing notes

- Settings, parsing, and payload builders live in `adapters/openrouter.py` next to the
  embedding precedent; unit tests cover order/fallback payload shape, rotation bound,
  throttle-vs-work budget split, host recording, and fingerprint stability.
- Review bar: cursor + antigravity on the implementing PR, same as the design PR.
