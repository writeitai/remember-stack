# Completing the engine storage-capture consumer

**Status: non-binding analysis.** This records the decision boundary for the
engine consumer of genuine provider storage evidence. It is not an implemented
collector, accepted financial mapping, populated measurement profile or
permission to enable managed storage charging.

## General provider scope and the managed role binding

The owner's accepted technical direction is a useful mountable.io capture
feature for its own users, including an organisation with one filesystem.
The provider's proposed binding amendment is
[FSIT #577 at 16111a1ab7ffe81e84a7197e21dfb79fe015260a](https://github.com/writeitai/fsit/blob/16111a1ab7ffe81e84a7197e21dfb79fe015260a/design/designs/scoped-storage-capture.md),
read on 2026-11-11. It selects one nonempty exact same-organisation/same-cell
set. Its review/merge and implementation are separate gates; the older
accepted source is not claimed to have already served this general feature.

Keeping a provider-wide count of four would force a single-filesystem user
to create empty padding. A separate one-filesystem path would duplicate
authority and identity rules. Use one exact-set protocol instead. Finite
qualified transport/batch/work bounds belong to operator capacity, not a new
customer quota. Smaller valid scopes avoid unnecessary work; larger scopes
still require their own bounded native/I/O/cost proof before enablement.

The UMC adapter independently requires its four distinct role filesystems.
Generalising the provider never permits missing roles, implicit sibling
expansion or extra requested scope in that adapter. Four-ID canonical request
and scope bytes/hashes stay identical; there is no compatibility verifier or
padding branch. Item identity, byte bases, native timing, component/member/ACK
contracts and commercial terms do not change.

## Narrow contract to settle

1. The engine owns a complete capture manifest: exact deployment/store
   bindings, requested instant and clock bracket, schema/classification
   identities, native physical component evidence, provider manifest identity,
   classified references and exact independent storage evidence membership.
   A maximum processing sequence cannot stand in for that set.
2. The provider adapter validates one D63 result and every page under the same
   exact four-set request. It matches opaque provider path identities to the
   engine's known keys in both directions. Unknown entries, missing pages,
   unresolved aliases or changed ownership cannot silently become zero bytes.
   Provider chunk/part/accounting counters retain their own observation bracket
   and never become an all-resource physical byte count at the cut.
3. The short engine physical/mutation guard and the provider witness cover the
   same possible values of the requested instant. The original bounded engine
   view survives paged extraction after those short guards release. No lock is
   held while waiting for delivery, customer funding or acknowledgement.
4. Customer quantity is separate from substrate evidence and resource
   obligation. The existing allocated PostgreSQL quantity cannot become a
   row-length estimate, nor can mixed-purpose physical pages be assigned by
   a name prefix or guessed fraction. The profile must state its complete
   purpose mapping and qualified physical mechanics.
5. Capture identity and acknowledgement name the exact immutable manifest and
   membership. A failed historic cut stays missing; a forward cut cannot
   backdate current bytes. Current-terms operator settlement must replace its
   old processing-watermark eligibility path atomically with the selected
   independent storage contract, with no compatibility fallback.

The existing proposal records independent intent/authority and disposition
shapes and the cost/enforcement vectors. This leaf must select the consumer
contract, explain its source-compatible operator mapping, and reconcile
affected binding designs. It must not hide an unchosen business policy inside
a typed interface. Measured allocated relations are not a populated
maintenance proof; a P3 serving role is not automatically an additional
physical copy; a failed processing outcome does not prove retained resources
disappeared.

## Work and limits

The implementation-facing design is being completed alongside the provider's
typed materialiser boundary. It will choose no new price, arbitrary upload/
entry/churn cap, free interval, minimum charge, cross-meter subsidy or release
coordinator. If a qualified current workload exposes a positive cost with no
permitted funding source, that exact vector goes to an explicit operator
decision; a guessed number is not evidence.

This work changes the planning corpus only. No implementation,
schema, credential, live resource, public documentation, paid reuse input or
customer-facing claim has changed.

## Selected boundary and rejected scope expansion

The [consumer design](../designs/storage_capture_consumer_design.md) selects
read-only evidence, classification and exact membership. It does not adopt
the proposal's all-writer pre-growth financial-permission system as a
prerequisite for observing resources. A parked deployment must still be able
to produce recovery/privacy evidence. Existing funded-growth and no-debt
invariants remain; positive excluded/unfunded exposure stays visible.

Native successful processing outcomes are actual members of the captured
engine view, not an inferred sequence prefix. Independently stored card,
failed, no-op and in-flight resources are still classified from reference
and provider facts. That is sufficient to separate observation from money;
it does not authorise an unheld charge or declare existing admission's
uncovered cost vectors solved.

The provider owner agreed the fixed item fields and five independent flags,
explicit null alias on non-links and regular/directory/symlink vocabulary.
Hard links keep their resolved supported kind and an alias group. Source
state strings are pending/uploading/sealed for chunks and
open/completing/committing/aborting for multipart. Retained includes uploading
and sealed; sealed is a subset. Original view-acquisition brackets remain
distinct from later enumeration times. This is coordinated wire intent,
not a currently served API or proof of current writer/profile qualification.

The decision leaves the measured physical quantity allocated, preserves
separate P3 origin and extra serving-replica evidence, and refuses an
unqualified mixed-purpose physical mapping. It chooses no row fraction,
free retained bytes, price or arbitrary product limit. The operator's
matching D55/D102 measurement/eligibility amendment remains required before
managed adapter implementation/use. First-enable populated/profile and
current-terms cost proof is distinct from this technical contract.

The provider's fixed invocation can finish materialising long after its short
metadata fence releases. Waiting for that final response while holding the
engine's short guard would violate the bounded-cut contract. The selected
consumer therefore proves and releases its own guard after its own T bracket,
materialises its original view independently, and validates the completed
provider bracket/release before publishing anything. Failed provider evidence
means no completed engine result, not a longer engine pause. This requires
neither an early provider callback nor another coordination service.

The first engine repeatable-read snapshot is acquired under that native guard.
Earlier authority/configuration queries must end their transaction before it
starts. A later table lock cannot refresh an already fixed view; this is an
implementation constraint on the original view, not a new historical repair
mechanism.
PostgreSQL's [LOCK description](https://www.postgresql.org/docs/18/sql-lock.html)
(retrieved 2026-11-11) explains why a later lock does not refresh an already
acquired repeatable-read snapshot. The implemented engine profile must still
qualify its actual pinned PostgreSQL/extension build; this source is not a
populated capture test.

The physical PostgreSQL values are sampled and spooled while the proved short
guard still excludes writers. A retained repeatable-read view preserves later
row/reference enumeration, not pg_relation_size values against post-cut DML.
The consumer therefore never relabels a later physical size as the requested
cut. PostgreSQL allocation, stored-object logical lengths and compressed K
object/pack lengths have separate explicit byte bases; reference lengths and
overlapping provider resource counters are not extra component sums. Exact
classification, accepted mapping, once-counted resource-set and component
evidence digest preimages make replay independently reproducible.
PostgreSQL's [object-size function contract](https://www.postgresql.org/docs/18/functions-admin.html#FUNCTIONS-ADMIN-DBSIZE)
(retrieved 2026-11-11) defines the relation/fork, table, index and TOAST disk
sizes. The requirement to sample these physical values under the guard follows
from that byte basis; an MVCC row view alone supplies no physical-size freeze.

## Existing v3 terminal digest compatibility

The control plane already matches terminal receipts using
[`canonical_outcome_digest`](https://github.com/writeitai/ultimate-memory-cloud/blob/dadb39562b1e2e139c46014bf9007fbba8a24828/src/ultimate_memory_cloud/billing/rating.py#L230-L237),
read on 2026-11-11. It normalises completed_at to UTC ISO/Z, serialises the
complete v3 JSON model with compact sorted keys and the JSON encoder's existing
ASCII escaping, then takes plain SHA256 without a capture-domain prefix.
The engine's existing ManagedDocumentVersionOutcome has the matching fields;
capture must not replace its UUID/string/int/null forms with new v1 forms.

The [six synthetic vectors](storage_capture_receipt_digest_vectors.json) were
computed with the actual existing engine and control-plane models and that
control-plane function. Two winter/summer offset pairs produce identical
digests for equal instants; microseconds and failed/null fields are preserved.
All six passed with Python 3.12.2 under both available Pydantic 2.11.7 and
2.13.4 environments. Both imported source blobs were checked byte-identical to
their recorded Git pins. This is model/digest interoperability evidence, not
an implemented engine storage digest, native capture or financial settlement.
Implementation must reproduce these expected bytes/digests independently in
the engine and keep its ordinary v3 provider-call/reuse tests.
