# Architecture

RememberStack does not treat a vector index as the database. A deployment’s memory lives in a **durable store**: PostgreSQL rows that record what was ingested, what sources claimed, what the system currently holds true, and when those beliefs changed — plus object storage for the bytes those rows point at. Git holds compiled and authored knowledge pages beside that store.

In the Compose self-host that store is PostgreSQL 19 plus MinIO; another deployment uses the same engine schema on PostgreSQL plus an S3-compatible bucket. The rules do not change with the vendor.

**Hard rule:** validity and invalidation live **only** in PostgreSQL. Search indexes are derived state beside the authority rows. They **nominate** candidates; PostgreSQL **confirms** live truth. Neither a lagging index nor a knowledge page can become independent authority.

## What lives where

![Three planes](/docs/diagrams/three-planes.jpg)

| Store | Holds | Authority |
| --- | --- | --- |
| **PostgreSQL** | Document lineages and versions, chunks, claims, entities, facts, evidence links, validity windows, processing state; rebuildable P1 vectors and BM25; live graph views | **Source of truth** for natural evidence rows. P1 and graph query structures are derived |
| **Object storage — raw** | Original uploaded bytes | Byte authority |
| **Object storage — artifacts** | Converted Markdown, structure, media sidecars | Representation authority (replayed, never regenerated in place) |
| **Object storage — corpus tree** | P3 browsable filesystem | Derived; rebuild from Postgres + artifacts |
| **Git** | Plane K compiled and authored pages | **Source of truth** for knowledge prose (authored words are irreducible; compiled pages recompile from stored facts) |

One line: **Postgres says what is true and when; object storage holds the bytes; git holds the prose we wrote about it.**

## How the store is shaped

The store is a **DAG across three planes**, not a single ladder. The plane a component lives in fixes its rules: triggers, authority, mutability, rebuild semantics.

```
  inputs (files, mail, web, audio, video, images)
      │
      ▼
  E0 files ─→ E1 chunks ─→ E2 claims ─→ E3 facts     Plane E — evidence store
    │                                    │           (Postgres + object storage)
    │              ┌─────────────────────┤
    ▼              ▼                     ▼
  P3 corpus fs    P1 search             live graph   Read models
                  indexes               (Postgres)

                  K knowledge pages (git)             Plane K — compiled + authored
```

| Plane | Meaning | Trigger | Mutability | Rebuild |
| --- | --- | --- | --- | --- |
| **E — Evidence** | What we ingested and adjudicated | Per-document chain | Append-only; windows close | n/a — it *is* the ground truth |
| **K — Knowledge** | What we concluded in prose | Debounced evidence change | Compiled rewrite / authored edit | Recompile (semantic) |
| **P — Projections** | How we reach it fast | Inline or scheduled | P1 and graph are live; P3 is immutable | P1 maintenance / P3 rebuild |

**E is what we ingested, K is what we concluded, P is how we reach it — and P always rebuilds from E.** K pages and P3 cross-link as consumers of each other; K is never a structural input to P1 or graph reads.

The conceptual *why* (testimony vs truth, two clocks, why indexes cannot be authority) is on [What is a memory system](/docs/why). This page is that store.

## Writes: evidence accumulates

![Ingestion pipeline](/docs/diagrams/ingestion-pipeline.jpg)

Every input walks one durable, inspectable pipeline. Stages are idempotent workers on a work ledger (retries, dead-letter, budgets). Writes may call models. Work is ledgered, versioned, and replayable. Reads never enqueue writes.

| Stage | Name | Job |
| --- | --- | --- |
| **E0** | Files | Store raw bytes; convert to Markdown via registered routes (smoke profile: Markdown passthrough; OCR/ASR/VLM when those routes are composed); structure sections; preserve locators |
| **E1** | Chunks | Deterministic blocks → retrieval-sized chunks with context prefixes |
| **E2** | Claims | Atomic grounded assertions (immutable) |
| **E3** | Facts | Entity resolution + relation/observation adjudication, supersession, contradictions |

Postgres holds metadata, claims, entities, facts, evidence links, and processing state. Object storage holds raw originals and converted representations.

Exhaustive write path: [Ingestion](/docs/ingestion) · [Pipeline stages](/docs/ingestion/pipeline) · [Lifecycle](/docs/ingestion/lifecycle).

## Reads: nominate, confirm, account

![Retrieval flow](/docs/diagrams/retrieval-flow.jpg)

**Reads use no LLM completion** (semantic paths may still embed the query). The motion is:

1. **Nominate** — P1 search, live graph SQL, open SQL, or an assured operation proposes candidates (P1 may lag; the graph does not).
2. **Confirm** — hydration against live Postgres re-reads validity, invalidation, contradiction membership, and testimony currency.
3. **Account** — the envelope states grain, freshness, drops, truncation, and typed negatives.

Mounted file reads skip step 2 by construction (snapshot files). Rule: orient on mounts; **verify load-bearing facts in the store**.

Agents reach the store through four surfaces with one precedence rule:

1. **Mounts** (when available) — prefer for navigate / read / `grep`
2. **API** — enforcement point for query-engine reads; open SQL + assured ops
3. **CLI** — the same operations for shell agents
4. **MCP** — the same operations for tool-using harnesses

Open query is sandboxed SQL over the `memory_v1` views plus typed live-graph helpers. There is no graph snapshot and no public Cypher surface. Exhaustive read path: [Retrieval](/docs/retrieval).

## Projections (how we reach it)

| Projection | Store | Serves |
| --- | --- | --- |
| **P1** | Same PostgreSQL (`pgvector` + `pg_textsearch`) | Vector + BM25 over chunks and claims; semantic search over fact labels and entities |
| **Live graph** | Same PostgreSQL (SQL/PGQ + recursive SQL) | Immediate neighborhood / path / as-of graph from committed entity and relation authority |
| **P3** | Object tree / mount | Browsable corpus filesystem (`ls` / `cat` / `grep`) |

P1 can be repaired from authority and P3 can be rebuilt. The graph is a live relational view plus catalog metadata, so there is no graph snapshot to rebuild.

## Knowledge sits beside the store

Git holds knowledge pages:

- **Compiled** — LLM writers produce citation-bearing prose; a deterministic driver owns staleness, routing, and commits.
- **Authored** — human/agent commitments (principles, plans). Evidence changes **flag** them; nothing rewrites them silently.

Compiled pages are semantically regenerable from stored facts plus recorded compile inputs. Authored words are irreducible. Agent contract and scopes: [Knowledge (Plane K)](/docs/knowledge).

## Registries (shared control data)

| Registry | Why it exists |
| --- | --- |
| **Entities** | Canonical IDs + aliases; merge transcripts |
| **Predicates** | Governed vocabulary with escape values |
| **Operations / saved queries** | Versioned query compositions; MCP renders from registry |
| **Ontology packs** | Domain extensions without forking the core |

Adding an operation is inserting a row — surfaces stay in lockstep.

## Scale posture

- Content-addressed reuse: identical bytes paid once.
- Edit-proportional reprocessing: unchanged chunks reuse claims/vectors.
- P3 builds are whole-corpus; P1 updates incrementally and graph reads are live.
- Spike-tested search and hub pagination at large row/edge counts (see project status / design spikes) — not a hosted SLA.
