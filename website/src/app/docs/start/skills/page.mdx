# Remember skill

<AppliesTo products={["self-hosted"]} />

The Remember skill teaches a coding agent how to look up decisions, cite the
source, save documents, and recover if it loses a write response. The skill
provides instructions. Your agent calls the Remember MCP server to use them.

## Install and discover

You need Node.js 22.20 or later with `npx`, an agent that supports Agent
Skills, and a self-hosted RememberStack engine. Follow the
[Quickstart](/docs/start/quickstart) to start the engine, then
[connect your coding agent](/docs/start/connect-your-agent) to give it MCP access.
Run this in the project where you start your agent:

```bash
npx skills add writeitai/remember-stack --skill remember
```

Choose your agent in the installer's picker. Open a new session in that
project so it discovers `remember`. In Claude Code, invoke `/remember`. In
Codex, invoke `$remember`. The [skills CLI documentation](https://skills.sh/docs)
covers other supported agents and their install paths.

## Store and find a note

Use a test deployment and ask your agent:

> Use the Remember skill. Save a Markdown note called `billing-handoff.md`
> with the text “John owns the invoice exporter for the billing migration.”
> Use source kind `file` and source reference `examples/billing-handoff.md`.
> Find the note by its returned document ID and tell me its file name and
> version ID.

On a fresh deployment, the ingest receipt has `created: true` and a
`version_id`. The agent can use `search_documents` with the returned
`doc_id` in `doc_ids` to find the stored document. Its file name and version
ID should match the ingest.

To ask who owns the invoice exporter, use the receipt's `pipeline.poll_with`
to [check readiness](/docs/guides/wait-for-readiness#over-mcp) first. Once the
note is ready, the agent uses `resolve_entity` and `facts_context` to look up
the answer. You should see John named with evidence from the note. If memory
does not have a fact, the agent can check `claims_and_sources_context` and
say what the source records.

## Retry a request

Reads such as `facts_context` and `pipeline_readiness` can be retried after a
timeout or transient failure. On `429`, wait for `Retry-After` seconds. MCP
exposes that delay as `retry_after` when available. If you hit the concurrency
limit, also let your in-flight calls finish. Use bounded backoff when there
is no server delay to follow. See [admission limits](/docs/reference/http-api#admission-limits).

If the ingest response goes missing, check whether another writer could have
advanced the source. With no intervening writer, send the same bytes with
the same source identity and metadata. If the first call stored the note,
the retry matches the latest version by its content hash. The receipt has
`created: false` and the existing `version_id`. Check readiness for that ID.
A new `version_key` or a replay of older bytes can create a version. See
[Re-ingesting the same bytes](/docs/concepts/documents-and-sources#re-ingesting-the-same-bytes-createdfalse).

For other writes with an unknown outcome, inspect current state before
trying again. For example, check whether the document is already archived
or whether a tag is already assigned. If you cannot verify the outcome,
stop and report what you know.
