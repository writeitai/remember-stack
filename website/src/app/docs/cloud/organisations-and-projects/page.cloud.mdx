# Organisations, projects and members

<AppliesTo products={["remember.dev"]} />

remember.dev has three levels. An **organisation** holds the money and the
people. A **project** is one memory. A **deployment** is the running copy
of RememberStack that serves that project. You work with organisations and
projects; the deployment is what your code connects to.

## Organisation: billing and the team

An organisation owns:

- the credit balance and the Stripe customer that pays for it;
- the monthly spending cap;
- the statements;
- the team: who is a member and who is an owner.

Every project in the organisation draws on the same balance. Signing up
creates a personal organisation for you, with you as its owner. You can
create further organisations for a team (`POST /v1/orgs`); each one has its
own balance and its own members.

## Project: one memory, one deployment

A project is the boundary of one memory. Each activated project gets
exactly one deployment with its own database, storage buckets, credentials,
model provider key and hostname:

```text
https://<deployment-id>.dp.remember.dev
```

Two projects never share a memory. If the billing migration team and the
support team each need their own memory, give each a project. If they need
to find each other's documents, they belong in one project.

A project has a display name, which owners can change, and a slug derived
from the first name, which never changes.

### The Default project

Signing up creates one project called **Default**. It has no deployment
yet. Your organisation's first credit purchase activates it: once Stripe
confirms the payment, remember.dev creates the Default project's
deployment. Nothing else creates the first deployment.

### Creating another project

An owner creates another project from **Projects** in the console. Each new
project needs its own activation Checkout:

1. You name the project and choose **Create and activate**.
2. remember.dev reserves a project slot and opens a Stripe Checkout for the
   activation purchase.
3. When Stripe confirms the payment, the credits go into the organisation's
   balance and remember.dev creates this project's deployment.

Abandoning the Checkout does not create a deployment. The project stays in
the list, not activated.

You can create another project only when:

- the organisation's billing is active (its first purchase went through);
- the Default project has been activated; and
- a project slot is free.

A new organisation has one project slot. The console shows **Project slots**
and says when all are in use. Ask [support](/docs/cloud/support) to raise the
limit; there is no self-service control for it yet.

### Activation and deployment states

The **Projects** page shows two things for each project.

**Activation** follows the paid activation:

| State | Meaning |
|---|---|
| `pending_checkout`, `awaiting_payment` | Checkout opened; payment not confirmed |
| `paid` | Payment confirmed |
| `requested` | The deployment has been requested |
| `waiting_capacity` | Paid, waiting for room on a remember.dev host. You are not charged for active compute while waiting |
| `cancelled`, `refunded` | The activation did not go ahead |
| `NEEDS_RECONCILIATION` | Payment and provisioning disagree; remember.dev resolves it. Contact support if it stays |

**Deployment** follows the running copy:

| Console label | API `state` | Meaning |
|---|---|---|
| Not started | none | No deployment yet |
| Requested | `requested` | Waiting to be provisioned |
| Provisioning | `provisioning` | Being created |
| Ready | `active` | Serving requests at its hostname |
| Blocked | `blocked` | Stopped. Usually the balance or a cap cannot fund the next day of active compute; see [Spend caps and auto top-up](/docs/cloud/spend-controls) |
| Recovering | `recovering` | Funded again and coming back on the same hostname |
| Offboarding | `disabled` | Being closed; see [Closing a project](/docs/cloud/leaving) |

The deployment's own readiness endpoint says whether it can take requests;
the state above is what remember.dev's control plane last recorded.

## Owners and members

Each person in an organisation is an **owner** or a **member**.

| Action | Owner | Member |
|---|---|---|
| See the organisation, its members and deployments | yes | yes |
| See the balance, ledger, statements and auto top-up settings | yes | yes |
| Buy credits, set the monthly cap, change auto top-up | yes | no |
| Create, rename and archive projects; set project sub-caps | yes | no |
| Assign people to projects | yes | no |
| Invite people, see pending invites | yes | no |
| Mint, list and revoke deployment API tokens | yes | no |
| Approve `remember login` for a deployment | yes | no |
| Request or close a project (offboarding) | yes | no |
| Change organisation settings (diagnostics opt-out) | yes | no |
| Open support records | yes | yes |

Owners see and administer every project in the organisation. In the
console and the project list, members see only the projects they have been
assigned to.

### Project membership

An owner gives a member access to a project by assigning them to it
(`POST /v1/orgs/{org_id}/projects/{project_id}/members` with the member's
`user_id`). Revoking the assignment takes access away and cannot be undone
by an old credential: each revocation advances a generation number that
credentials are checked against.

The console does not yet have a screen for project assignment; use the
[remember.dev API](/docs/reference/cloud-api).

<Callout type="note">

Project membership decides which projects a member sees in the console
and whether they can upload to a project. It is not a permission system
inside the memory. There are no per-document or per-source permissions:
anyone who can read a project's memory can read all of it.

</Callout>

## Inviting people

Owners invite people under **Team → Invite member**. An invitation:

- names an email address and a role (`MEMBER` by default, or `OWNER`);
- expires after 7 days; an owner can resend or revoke it;
- can be accepted only by a signed-in account whose verified email address
  matches the invitation.

An owner can also add someone who already has a remember.dev account
directly (`POST /v1/orgs/{org_id}/members`).

There is no way yet to remove a member from an organisation or change their
role, in the console or the API. Ask [support](/docs/cloud/support).

## Archiving a project

An owner can archive a project that has no deployment and no activation
payment in progress, which frees its slot. A project with a deployment is
archived as the last step of [offboarding](/docs/cloud/leaving); archiving never
stops a deployment or its charges on its own.
