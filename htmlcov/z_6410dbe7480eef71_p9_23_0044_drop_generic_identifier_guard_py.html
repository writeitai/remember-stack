1"""Drop the generic-identifier guard; a shared name is not a weaker name. 

2 

3revision: p9_23_0044 

4 

5The guard recorded, per normalized string, how many distinct entities it 

6linked, and flagged the string once that count reached two. Blocking then 

7sorted on that flag AHEAD of match score, so a 0.95 trigram hit on a shared 

8name ranked below a 0.31 hit on an unshared one and could be truncated out 

9of the candidate list entirely. 

10 

11The premise was wrong. Counting entity rows is not counting people: D95 

12forbids T0 from auto-merging, so the resolver deliberately mints a second 

13row for one real person, and the guard then read its own conservatism as 

14proof that the name was generic. Two Jan Nováks -- whether one person 

15recorded twice or two unrelated people -- are exactly the case the resolver 

16exists to adjudicate, and demoting both made the adjudication harder. 

17 

18The flag was never adjudication evidence either: it lived only in ORDER BY 

19clauses, never on a candidate, never in decision features, never seen by T3 

20or T4. That is not the same as harmless. Blocking order decides which 

21candidates survive truncation to blocking_limit and which one T4 is told to 

22prefer, so an inverted ranking could change an authoritative verdict while 

23leaving no trace in the decision record it helped produce. 

24 

25D21's original intent -- a genuinely promiscuous signal like a role address 

26or a shared reception number should not weld strangers together -- is not 

27abandoned; it is left to the mechanisms that actually adjudicate identity 

28(T3 profile evidence, T4, and the D21 resolution_exclusions cannot-link 

29edges), rather than to a blocking-stage counter with a floor of two. 

30 

31The table is dropped rather than left unread. It is a per-deployment cache 

32with no lineage provenance -- keeping a stale copy of erasable surface 

33strings that nothing consumes is a retention cost with no benefit. 

34"""

46# One statement, one transaction, and no scan. The table is small by 

47# construction (one row per distinct normalized lemma) and, as of the 

48# revision that accompanies this one, is written by nothing. 

49# 

50# It is NOT a single-table lock, which is worth stating because the obvious 

51# assumption is wrong. `generic_identifier_guard.deployment_id` REFERENCES 

52# `deployments`, and dropping the table must drop that constraint, so 

53# PostgreSQL takes AccessExclusiveLock on `deployments` as well -- measured: 

54# 

55# public.deployments AccessExclusiveLock 

56# public.generic_identifier_guard AccessExclusiveLock 

57# public.generic_identifier_guard_pkey AccessExclusiveLock 

58# (plus the table's TOAST relation and its index) 

59# 

60# `deployments` is the tenancy root that nearly every query joins, and 

61# AccessExclusiveLock blocks readers as well as writers. The saving grace is 

62# duration, not scope: there is no scan and nothing to rewrite, so the lock 

63# is held only for the catalog updates in this one short transaction. Treat 

64# it as a brief global stall, not as a free operation, and apply it the way 

65# any other DDL against `deployments` would be applied. 

66_DROP_TABLE = "DROP TABLE IF EXISTS generic_identifier_guard" 

67 

68 

69# Plain CREATE, deliberately. An earlier revision of this file used 

70# IF NOT EXISTS plus an ON CONFLICT upsert; that was wrong twice over. 

71# PostgreSQL DDL here is transactional, so a run interrupted between the two 

72# statements below rolls back BOTH -- the partial state it claimed to guard 

73# against cannot occur. And the upsert only rewrites rows that collide, so 

74# any pre-existing row with no surviving alias group would have been left 

75# behind, quietly producing something that is not the reconstruction it 

76# advertises. 

77# 

78# If this table exists when the downgrade runs, the database disagrees with 

79# its own revision stamp. That is a real inconsistency and the migration 

80# should stop, not paper over it. 

81_RECREATE_TABLE = """ 

82CREATE TABLE generic_identifier_guard ( 

83 deployment_id uuid NOT NULL REFERENCES deployments, 

84 normalized_lemma text NOT NULL, 

85 distinct_entity_count integer NOT NULL, 

86 is_downweighted boolean NOT NULL DEFAULT true, 

87 reason text, 

88 evaluated_at timestamptz NOT NULL DEFAULT now(), 

89 PRIMARY KEY (deployment_id, normalized_lemma) 

90); 

91COMMENT ON TABLE generic_identifier_guard IS 

92 'Surfaces that link too many entities to be identifying (D21). Down-weighted so they stop driving merges; the merges they already caused are re-evaluated — enumerated via merge_events.trigger_lemmas (below).'; 

93""" 

94 

95# Recreating the table EMPTY would not restore prior behaviour, only prior 

96# compatibility. The old reader used coalesce(is_downweighted, false), so 

97# old code runs fine against an empty table -- but every previously flagged 

98# lemma silently becomes unflagged, and the first fuzzy resolution after a 

99# rollback would rank differently than it did before the upgrade. The old 

100# writer only refreshes a lemma when that lemma is touched again, so the 

101# gap persists for anything not re-ingested. 

102# 

103# So the downgrade rebuilds the cache from the aliases that are still there, 

104# using the same COUNT(DISTINCT entity_id) and the same floor of 2 the old 

105# writer used. This is a reconstruction of a derived cache from existing 

106# rows, not seed DML; `evaluated_at` is honestly stamped now() because that 

107# is when the reconstruction happened. 

108_REBUILD_TABLE = """ 

109INSERT INTO generic_identifier_guard ( 

110 deployment_id, normalized_lemma, distinct_entity_count, 

111 is_downweighted, reason, evaluated_at 

112) 

113SELECT deployment_id, normalized_lemma, COUNT(DISTINCT entity_id), 

114 COUNT(DISTINCT entity_id) >= 2, 'promiscuous-lemma', now() 

115FROM aliases 

116GROUP BY deployment_id, normalized_lemma 

117"""

120def upgrade() -> None: 

121 """Remove the promiscuous-lemma cache and its inverted ranking input.""" 

122 # Fail fast rather than queue. An AccessExclusiveLock REQUEST on 

123 # `deployments` blocks every later query behind it while it waits, so an 

124 # unbounded wait behind one long read would stall the tenancy root far 

125 # longer than this migration itself ever does. Timing out and retrying in 

126 # a quieter moment is strictly safer than blocking the queue. 

127 op.execute("SET LOCAL lock_timeout = '5s'") 

128 op.execute(_DROP_TABLE) 

129

131def downgrade() -> None: 

132 """Recreate the cache and rebuild it from the surviving aliases.""" 

133 op.execute("SET LOCAL lock_timeout = '5s'") 

134 op.execute(_RECREATE_TABLE) 

135 op.execute(_REBUILD_TABLE)
