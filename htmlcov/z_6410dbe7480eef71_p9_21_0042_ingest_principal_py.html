1"""Record the typed principal that created each document version. 

2 

3revision: p9_21_0042 

4 

5Ingest attribution is a *typed principal at version grain*: the engine records 

6WHO created a version without becoming a per-user authorization system (D50 

7keeps content-level authorization a non-goal; this adds attribution only). 

8 

9Three kinds are distinguished because they are genuinely different referents: 

10``user`` is a person, ``api_credential`` is a machine credential that a person 

11once minted, and ``service`` is the deployment's own automation. Attributing 

12credential activity to the human who minted the token would be false 

13attribution, so the kind is stored, never inferred away. 

14 

15Attribution is creation-scoped and immutable: the column is set when a version 

16row is inserted and never updated. Under D55 identical bytes return the 

17existing version with ``created=False``, so a later submitter of the same bytes 

18changes nothing here — that attempt is an operator/control-plane audit event, 

19not a second attribution. 

20 

21``external_ref`` is opaque to the engine (the caller's stable id for the 

22principal). It is treated as erasable PII: a person-grain forget must be able 

23to enumerate and scrub principal rows and the bindings that reference them. 

24""" 

25

40_CREATE_TABLE = """ 

41CREATE TABLE ingest_principals ( 

42 principal_id uuid PRIMARY KEY, 

43 deployment_id uuid NOT NULL REFERENCES deployments, 

44 kind ingest_principal_kind NOT NULL, 

45 external_ref text NOT NULL, -- opaque caller id; erasable PII 

46 first_seen_at timestamptz NOT NULL DEFAULT now(), 

47 last_seen_at timestamptz NOT NULL DEFAULT now(), 

48 UNIQUE (deployment_id, kind, external_ref), 

49 UNIQUE (deployment_id, principal_id) -- composite-FK target (tenancy, §0) 

50); 

51COMMENT ON TABLE ingest_principals IS 

52 'Typed ingest actors (user | api_credential | service). external_ref is the 

53 caller''s opaque stable id and is erasable PII. A credential is never 

54 collapsed into the person who minted it.'; 

55""" 

56# No separate lookup index: UNIQUE (deployment_id, kind, external_ref) already 

57# provides one. A duplicate would double write cost and, worse, keep a second 

58# physical copy of erasable PII. 

59 

60# ONE transaction, and no index. 

61# 

62# An earlier revision built a partial index on ingested_by_principal_id 

63# CONCURRENTLY inside an autocommit block. Alembic commits before entering 

64# that block, so an interruption stranded committed objects with the 

65# revision unstamped and the rerun died on `type … already exists`. The 

66# fallback advice -- pre-build it by hand -- was impossible: the column does 

67# not exist before this migration runs. 

68# 

69# The real answer is that the index is not needed. Nothing reads by 

70# principal: `version_principal()` anchors on the version primary key and 

71# joins principals by theirs. A partial index would be pure write cost for 

72# a query this slice does not have. The bounded "documents by principal" 

73# operation is a later slice; it can add the index in its own revision, 

74# concurrently, once the column already exists. 

75# 

76# What remains is small enough to be one atomic transaction: it commits 

77# whole or rolls back whole, with no lock held for a scan. 

78_ADD_COLUMN = """ 

79ALTER TABLE document_versions 

80 ADD COLUMN ingested_by_principal_id uuid; 

81COMMENT ON COLUMN document_versions.ingested_by_principal_id IS 

82 'The principal that CREATED this version (immutable, creation-scoped). NULL 

83 for versions ingested without attribution, including every pre-migration 

84 row. ON DELETE SET NULL keeps a principal erasure from destroying the 

85 version itself.'; 

86""" 

87 

88# NOT VALID, and deliberately never validated here. 

89# 

90# A validated ADD CONSTRAINT sequentially scans `document_versions` while 

91# holding ShareRowExclusiveLock, so the outage grows with the table -- 

92# measured, with a concurrent UPDATE timing out. NOT VALID is scan-free 

93# (seq_scan=0), which removes that table-size dependence. 

94# 

95# It is NOT lock-free: PostgreSQL 19 still takes ShareRowExclusiveLock for 

96# ADD FOREIGN KEY ... NOT VALID, held until this atomic transaction commits, 

97# and a concurrent writer will wait on it. The difference that matters is 

98# bounded-and-brief versus proportional-to-row-count. 

99# 

100# Nothing is skipped by doing so. NOT VALID only forgoes checking rows that 

101# already exist, and `ingested_by_principal_id` was added by this same 

102# migration, so every existing row is NULL by construction and cannot 

103# violate anything. The constraint is fully enforced for every subsequent 

104# insert and update either way. 

105# 

106# Splitting VALIDATE into its own transaction would restore the planner's 

107# `convalidated` flag, but that needs a second revision or an autocommit 

108# block (which already cost us restart safety once). An operator who wants 

109# the flag can run it online at any time -- VALIDATE takes only 

110# ShareUpdateExclusiveLock and does not block writers: 

111# ALTER TABLE document_versions 

112# VALIDATE CONSTRAINT fk_document_versions_ingest_principal; 

113_ADD_FK = """ 

114ALTER TABLE document_versions 

115 ADD CONSTRAINT fk_document_versions_ingest_principal 

116 FOREIGN KEY (deployment_id, ingested_by_principal_id) 

117 REFERENCES ingest_principals (deployment_id, principal_id) 

118 ON DELETE SET NULL (ingested_by_principal_id) 

119 NOT VALID; 

120"""
