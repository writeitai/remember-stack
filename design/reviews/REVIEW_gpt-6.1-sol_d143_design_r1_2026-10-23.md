2. **P1 must fix — Oldest-first claims backfill can permanently retire claims that the latest version subsequently reuses.** Location: `plan/designs/processing_layers_design.md:156–173`, `:222–244`, §5.5.

   Consider a living lineage with v1 and v2 already stored while claims were off, with unchanged sections in both. E0 already points `documents.current_version_id` at v2. Backfill grounds v1, opens its claims tail, deletes its claims gap, and advances v2. It is legal for v1's reconcile worker to run before v2's Ground/Claimify workers attach the reused claims. `src/rememberstack/workers/reconcile.py:106–125` reads the lineage's *current stored version*, not a backfill processing frontier; `src/rememberstack/spine/lifecycle.py:917–945` therefore identifies v1's claims as absent from v2 and retires them. Later v2 reuses those same claim IDs, but `src/rememberstack/spine/claim_catalog.py:116–201` and `:460–473` only insert occurrence links; they do not restore currency. Ordinary reconcile only computes retirement transitions. The existing restoration helper is used for version deletion, not this path (`src/rememberstack/spine/lifecycle.py:258–289`; `src/rememberstack/workers/reconcile.py:578–587`). The unchanged content can finish backfill with non-current testimony and disappear from current claim retrieval.

   The boundary/completion lineage locks do not prevent this schedule: the currency handler executes separately, after the extract-barrier transaction released its lock. Waiting for each older version's whole tail before extracting the next would not by itself fix the premature retirement against the already-stored latest version either.

   **Fix:** define the lineage's currency settlement frontier during claims backfill. Do not retire against a newer version until that version's occurrence set is complete; alternatively define an explicit, ledgered restoration protocol that makes subsequent reuse current again. Preserve claim IDs, text origins, and all reuse hashes rather than fixing this by re-extraction. Require a living-lineage regression with the older reconcile deliberately scheduled before newer occurrence attachment, checking current testimony as well as provider counts.

3. **P1 must fix — The boundary ordering rule ignores unfinished predecessors that entered a layer without a gap.** Location: `plan/designs/processing_layers_design.md:133–151`, `:236–244`, §6.2.

   Gaps are created only for versions that *skip* a boundary. An ordinary all-on v1 can already have queued E2 work, then have that work held when claims are switched off. It has no claims gap. With claims off, v1 is source-ready; v2 may be accepted and still be converting when claims are switched back on. `setup` sees no claims gaps, marks coverage complete, and seeds nothing. When v2 finishes `embed_chunk`, the all-on/complete shortcut, or the “earlier gap” test, admits it even though v1's held extraction has not finished. v2 can now pay Selection/Claimify calls for unchanged content before v1 publishes reusable products.

   This is not prevented by Advance's stronger “every earlier source-complete version has completed this layer” condition: that condition is absent from boundary admission, and there may be no backfill gap to advance. The actual reuse lookups are strictly earlier-version lookups (`src/rememberstack/spine/selection_catalog.py:113–149`; `src/rememberstack/spine/claim_catalog.py:386–406`), so a newer version cannot repair the unnecessary work later. The same gapless in-flight distinction affects facts ordering and coverage after off/on transitions.

   **Fix:** use one actual predecessor-completion predicate for both admission and advancement in a layer-managed lineage, including already-entered/held/dead-lettered work, or materialize the necessary unfinished-version tracking when changing configuration. Absence of a gap must not imply completion. Specify how this preserves the untouched all-on path, and test off/on with an entered but unfinished predecessor and a successor crossing its boundary during the restart/backfill.

4. **P1 must fix — Switching facts off can strand the enabled claims tail, and even previously ready versions cease to satisfy the new reconcile expectation.** Location: `plan/designs/processing_layers_design.md:115`, §4.2–§4.4, §6.1.

   The claims tail is opened only when a version *does not enter facts*. If v1 already crossed the extract barrier and its normalization/observation work is queued when facts are switched off, that work is held. Nothing opens v1's `embed_claim` or claims-only reconcile. In the actual chain, claim embedding is not enqueued until `complete_entity_obs_flush` or `complete_empty_obs_flush` (`src/rememberstack/spine/work_ledger.py:453–658`); the full reconcile is enqueued by `AdjudicateSupersessionHandler` (`src/rememberstack/workers/e3.py:757–776`). An enabled claims layer can therefore remain unembedded and unready indefinitely while facts are off.

   Independently, a version that already finished the entire old pipeline has a succeeded full reconcile, not a `reconcile-2026.07:claims` row. The proposed exact-component readiness map now demands the latter. `src/rememberstack/spine/readiness.py:196–272` keys status by `(version_id, stage, component_version)`, so such a version becomes missing/unready with no gap and no mechanism to create the missing row. “Readiness stops expecting facts” is insufficient.

   **Fix:** define an idempotent transition that ensures the claims tail for already-entered, partially processed versions when facts are disabled. Define a succeeded full reconcile as sufficient evidence for claims-only readiness, or explicitly create the required claims completion evidence without rerunning extraction. Revise setup's “nothing else is written” rule accordingly. Test switching off at each existing E3 handoff and inspecting an already fully ready version.

5. **P1 must fix — The specified locking does not make configuration changes or coverage completion race-free.** Location: `plan/designs/processing_layers_design.md:102–120`, `:129–131`, `:234–259`; `plan/designs/postgres_schema_design.md:367–395`.

   First, in the required default state there is no layer row to lock. A boundary's `SELECT ... FOR SHARE` of that absent row cannot serialize against setup's first insertion of an off configuration. The boundary may decide “all on” before the insertion and commit its handoff afterward, without recording the gaps that the new state requires.

   Second, lineage locks do not serialize the global last-gap test. Let A and B be the only remaining gaps in different lineages. Two completion transactions each delete their own gap, each still sees the other's uncommitted gap, neither sets coverage complete, and both commit. There are now no gaps and no future completion to change the stored `backfilling` value. Conversely, an unlocked coverage decision can race a new gap insertion. Share-locking the layer row does not serialize these writers; upgrading share locks to update locks also needs an explicit order to avoid deadlocks. The documents additionally call setup the only writer of the entire layer-state table, while §5.3 requires workers and deletion paths to write its coverage columns.

   **Fix:** give setup, boundary admission, seeding, gap deletion/insertion, and coverage settlement one explicit lock/isolation protocol, with a fixed lock order and a fence that exists even in the no-layer-row state. Recheck live gap absence under serialization before publishing complete. A simpler alternative is to store only the configured booleans and derive coverage from indexed live gaps, removing the mutable duplicate coverage state and its zero-crossing protocol. Correct the writer ownership comments whichever approach is chosen. Require concurrent last-two-gap and first-configuration-change tests.

6. **P1 must fix — Gap deletion is not a completion event, and late boundaries can recreate gaps for deleted versions.** Location: `plan/designs/processing_layers_design.md:218–226`, `:236–259`, §6.3.

   If v1 is an entered, dead-lettered backfill head and v2 is an unentered gap, deleting v1 removes its gap but does not execute Advance: §5.3 names completion as the only driver after setup. v2 then has no predecessor blocking it and no event that will enter it. This matters for operator version deletion, which preserves other versions of the lineage (`src/rememberstack/workers/reconcile.py:561–595`), not just public deletion of an entire lineage.

   In the other direction, an `embed_chunk`/extract attempt claimed before deletion can finish afterward. The boundary tables unconditionally record gaps when a layer is disabled/deferred; they do not require the version and document still to be live. Deletion may already have removed their gaps. Since the table has no FK, a late completion can recreate an orphan gap. Setup seeds only live versions, so that row has no backfill path. The proposed advisory lineage lock also is not the existing D135 document-row lock used by deletion and re-ingest (`src/rememberstack/workers/reconcile.py:713–724`; `src/rememberstack/spine/lifecycle.py:798–804`).

   **Fix:** make removal of a blocking version advance the surviving lineage in the same serialized transaction, and make every boundary/seed recheck document/version liveness under the deletion-compatible fence before writing or entering a gap. Late completions must discard deleted targets and settle coverage, not recreate their gaps. Add both delete-the-head and deletion-versus-late-boundary schedules, including a dead-lettered head and a zero-chunk successor.

7. **P1 must fix — “Deletion is never gated” needs an execution path for late cleanup, not only an exemption for `hard_forget`.** Location: `plan/designs/processing_layers_design.md:180–183`, `:300–307`, §4.2.

   D135 deliberately allows already-processing documents to finish after deletion. `ReconcileHandler._retire_deleted_testimony` explains why: late pipeline work can recreate testimony, support, and T4 document bindings after the original deletion cascade (`src/rememberstack/workers/reconcile.py:272–354`). That method clears/rebuilds bindings, recounts/closes the full affected scope, refreshes profiles, and requests window reviews. Under D143 its *full reconcile work row belongs to facts* and cannot be claimed while facts are off. The claims-only mode is explicitly forbidden from performing the fact cleanup. If a held intermediate stage has not yet enqueued reconcile, even exempting an existing reconcile row is insufficient.

   Thus a direct public deletion can run once while an already-claimed normalizer/adjudicator finishes afterward, with no guaranteed ungated cleanup to remove the late contribution. The initial deletion operation and the unlayered hard-forget stage do not cover this race.

   **Fix:** specify an ungated deletion-settlement path, including how late completions trigger it without waiting for disabled intermediate stages, and distinguish it from ordinary fact ingestion in the work-claim gate. Preserve the complete D135 cleanup scope, not only claim currency transitions. Test deletion while an E3 attempt is already running, with facts remaining off afterward, and assert closed support and cleared document bindings without enabling facts again.

8. **P1 must fix — Importing claims-only transitions does not settle already-finalized connector cycles.** Location: `plan/designs/processing_layers_design.md:169–173`, §5.6; `plan/designs/evidence_lifecycle_design.md:288–319`.

   Full reconcile does not always close source-acted zero-support facts itself. For a version with `sync_cycle_id`, `src/rememberstack/workers/reconcile.py:169–188` deliberately defers closure to `CycleFinalizer`. The latter claims a cycle once (`:453–463`); `src/rememberstack/spine/lifecycle.py:1429–1509` excludes cycles whose `finalized_at` is already set. The finalizer's `_close_lineage_zero_support` reads the existing counts; it does not redo the missing recount (`src/rememberstack/workers/reconcile.py:508–542`).

   Concrete off/on/off-history case: facts-on v1 supports R; facts-off v2 removes its only claim in connector cycle C. Claims-only reconcile retires that claim without recounting R. With no new fact stages, C can finish/finalize while facts are off, observing R's old nonzero stored count. When facts are enabled, v2's full reconcile imports the retirement and recounts R to zero, but still skips closure because C is cycle-stamped. C will not finalize again. R can remain open with zero support indefinitely. Merely unioning transitions of the same version does not address this.

   Holding the finalizer wholesale is not a complete alternative either: its source-deletion sweep is part of the ungated deletion contract, and its current readiness query can also be blocked by held fact work.

   **Fix:** define layer-aware connector-cycle settlement, including a durable fact-settlement generation or another idempotent path for imported transitions whose original cycle already finalized. Preserve the move-versus-retract barrier and LOSSY-cycle guard, and keep source-deletion cleanup runnable. Test facts on → off for a removal cycle → cycle finalization → on, and a cycle with held fact work and a source deletion.

9. **P1 must fix — Static function/operation layer declarations miss argument-dependent reads of excluded facts.** Location: `plan/designs/processing_layers_design.md:328–345`, `:382–399`.

   `semantic_claims` and `lexical_claims` are classified as claims-only. Their published `entity_id` filter is implemented using `memory_v1.mentions_live` (`src/rememberstack/surfaces/query_sandbox/nomination.py:39–45`, `:553–571`). A sandbox statement such as `SELECT * FROM semantic_claims($1, 20, $2)` with `$2 = {"entity_id": "..."}` therefore reads facts-owned mentions even though its only caller-visible function is mapped to claims. With facts disabled it can use retained stale mention data or silently return an empty scoped result. With facts excluded per request it bypasses the intended selection. Checking referenced SQL names alone cannot see this generated dependency.

   The assured-operation table recognizes `entity_ids` as a facts dependency, but only specifies refusal when facts are *unserved*. The §7.1 rules still admit `layers=sources` plus `entity_ids` on an otherwise all-on deployment: the operation has a nonempty layer intersection and no explicitly requested off layer. Its source-channel entity scoping also reads mentions (`src/rememberstack/surfaces/query_engine.py:1699–1709`, `:3219–3297`). The design does not specify what happens when that mandatory dependency is deliberately excluded.

   **Fix:** distinguish optional retrieval channels from mandatory argument-dependent dependencies. Validate both after decoding bound filters/arguments and before any nomination, query embedding, planning, or confirmation. Define consistent error/status semantics for excluded mandatory dependencies as well as disabled ones. Do not silently ignore an entity filter, and do not classify all unfiltered claim functions as facts. Cover literal and parameter-bound sandbox filters and entity-scoped operations with facts both off and excluded.

10. **P1 must fix — The facts-backfill history boundary rests on an incorrect claim about E3's inputs.** Location: `plan/designs/processing_layers_design.md:281–286`; `plan/analysis/processing_layer_toggles.md:274–280`.

   “E3 reads only current testimony” is not true of the ordinary handlers the backfill is required to reuse. `_SELECT_CLAIMS_FOR_NORMALIZE_FANOUT` includes every matching occurrence, without a currency predicate (`src/rememberstack/spine/work_ledger.py:1793–1805`). `claim_for_normalization` selects by claim ID alone (`src/rememberstack/spine/claim_catalog.py:526–535`), and E3 proceeds to normalization/resolution/staging (`src/rememberstack/workers/e3.py:255–299`, `:324–344`). Adjudication's snapshot likewise includes the incoming claim even when `is_current_testimony` is false (`src/rememberstack/spine/fact_application_inputs.py:239–288`). This is not merely excess normalization cost: with no existing candidate facts, `src/rememberstack/spine/fact_adjudication.py:734–742` chooses a new fact deterministically, and `src/rememberstack/spine/apply_fact_decision.py:101–146` inserts it without a current-testimony guard.

   A living v1 claim removed by v2 before facts were enabled can therefore be normalized and become a fact during v1's backfill. A later recount/closure cannot make “never becomes a fact” or “history starts when facts covers it” true retroactively; it has already produced identity, evidence, and adjudication history. Depending on cycle settlement it can also leave an open zero-support fact.

   **Fix:** choose and specify the actual living-lineage backfill policy. If the declared current-only policy is retained, add a deterministic eligibility rule for backfill normalization/application, with matching expected-set/barrier/completion semantics for skipped stale claims and races with currency changes. If historical assertions are intentionally processed, rewrite §5.6 and specify their settlement/cost semantics instead. Do not rely on a prompt seeing `current_testimony=false`. Test a removed claim with no candidate fact and count normalization/adjudication calls.

11. **P1 must fix — Receipt completeness can be certified against a different processing profile from the one measured.** Location: `plan/designs/processing_layers_design.md:199–212`.

   The proposed profile ID is fixed at measurement time, but `profile_complete` is defined using readiness under the layers enabled *now*. Measurement receipts are immutable (`src/rememberstack/spine/managed_metering.py:52–108`; `src/rememberstack/workers/e0.py:369–393`), while `_materialize_outcomes` obtains the current readiness report and converts it directly to a succeeded, profile-complete receipt (`src/rememberstack/spine/managed_metering.py:335–408`). `ManagedDocumentVersionOutcomeV2` explicitly treats that completeness as the evidence required for billable success (`src/rememberstack/model/metering.py:56–84`).

   Measure a version with `doc-text-standard-v1`, then turn facts off before it completes. Under this design the reduced readiness list can produce `profile_complete=true` for a standard-profile measurement whose fact work never ran. Conversely, enabling facts between a sources-only measurement and its outcome forces the outcome to wait for or fail on work outside the measured profile. This is an engine receipt-truth issue, separate from how the cloud prices a later backfill.

   **Fix:** separate mutable serving readiness from completeness of the immutable measured profile. Specify either profile-pinned completeness checks or a precise transition/terminalization protocol for outstanding measurements when configuration changes; never certify an uncompleted measured profile as complete. Keep pricing outside the library. Add in-flight profile-change tests in both directions and preserve the existing standard profile ID and default receipts exactly.

12. **P2 should fix — Successful sandbox reads have no way to disclose incomplete layer coverage.** Location: `plan/designs/processing_layers_design.md:347–399`, §8; analysis §6.2.

   The analysis promises a `backfilling` notice when a layer is enabled but incomplete. The binding design adds notices only to `Envelope`. SQL and saved-query execution return `QueryResult/v1`, not Envelope (`src/rememberstack/surfaces/query_sandbox/result.py:104–142`; `src/rememberstack/surfaces/http_api.py:1111–1135`). §7.5 only rejects off/excluded layers. A facts query during backfill can therefore return `empty_result=true` with no indication that the relevant versions have never reached facts. Discovery's optional deployment state does not disclose the state at this query's execution snapshot.

   **Fix:** specify how QueryResult reports coverage for its actual referenced layers, using an optional conditional extension or its existing warnings/provenance mechanism consistent with finding 1. Apply it to direct execution, explain, and saved queries as appropriate, preserve byte-identical all-on results, and test an empty result during backfill.

13. **P2 should fix — The acceptance contract overstates claim-ID reuse and misses the fixtures needed to prove the no-disabled-read invariant.** Location: `plan/designs/processing_layers_design.md:432–453`, especially test 6.

   Test 6 requires every v2 chunk other than the edit and its same-section neighbours to reuse v1 claim IDs. D122's previous-eight-Selection-hashes window can legitimately change Claimify identity beyond those neighbours, including across a section boundary. §5.5 acknowledges that boundary, and CLAUDE.md Rule 4 explicitly requires the known D122/packing cases to be named expected failures rather than silently weakened. The unqualified claim-ID assertion contradicts that test discipline.

   Separately, disabling the visible claim channels is not enough to prove no claim read. `_claims_and_sources_context_in_snapshot` always supplies four claim/chunk probes to `_touched_pending` (`src/rememberstack/surfaces/query_engine.py:1750–1761`); with a periodised, non-selectable in-force version the D140 probe executes additional nominations (`:472–554`). A statement-capture fixture with no pending in-force version never exercises this hidden path. The design should require the selected layers to control these probes and their freshness accounting too.

   **Fix:** assert claim-ID reuse where the full Claimify identity/remap is unchanged, assert Selection/text-origin identity separately, and include explicit D122 and packing-boundary fixtures under Rule 4's known-gap policy. Add a pending periodised-lineage fixture for both claims-off and `layers=sources`, capturing all probe/confirmation SQL and checking `scope_pending` honesty. Extend the concurrency cases to zero-chunk versions, dead letters/replay, deletion, and a layer switched off during an entered backfill, rather than only the two-version happy path.

Explicit non-negotiable checks:

- **DEFAULT-ON: not established by this design.** The booleans default true, no-row means all on, and §4 intends to retain the exact current twelve-stage readiness sequence and component versions (`src/rememberstack/profiles/selfhost.py:1685–1723`; `benchmarks/locomo/protocol.py:51–107`). However, finding 1 directly violates the default operation-descriptor bytes and query-surface hash promise. The current LoCoMo manifest pin is `f91c463643b59a1608c91cee7625fcc95c1802d8f99bdeab16d29d599b91705f`; changing that pin is not an acceptable fix. Default tests must include HTTP response-model serialization and direct MCP/SDK model dumps, `GET /operations`, `GET /deployment`, both MCP catalogues/input schemas, the generated manifest, and protocol pins. Use field-specific omit-if-empty serialization for opt-in notices; global `exclude_none`/`exclude_defaults` would also remove existing fields and change bytes.
- **RULE 4 / INCREMENTAL INGESTION: not established by this design.** Keeping chunks and their creation-time hashes/origins is the correct foundation: `src/rememberstack/workers/e1.py:179–203` fixes text origin at chunk creation, `:642–705` defines the unchanged extraction/reuse inputs, and `:267–275` uses the existing D80 carry-forward lookup. The diff itself changes no chunker, header fact, text-origin rule, extractor, embedding policy/model pin, or reuse-key input. Nevertheless, findings 2–6 admit incorrect testimony, duplicate paid extraction of unchanged content, and stranded lineages. The backfill ordering/state protocol must be corrected without rekeying, re-chunking, or re-embedding the corpus. Existing known Rule 4 gaps remain known gaps, not features solved by D143.

The deployment-only scope, two default-true settings, source/claim/fact split, reuse of ordinary handlers, and separate implementation plan are reasonable simplifications. No new Rule 2 phased/MVP scope or Rule 3 cloud-owned correctness mechanism is needed. Deriving coverage rather than storing it would remove meaningful machinery; it would not remove the need for a precise lineage admission, currency, and deletion-settlement protocol.
