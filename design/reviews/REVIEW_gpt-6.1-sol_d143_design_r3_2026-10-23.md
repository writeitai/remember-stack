   Selecting only current claims for the D88 fan-out and making a retired incoming application “contribute nothing” does not specify how the existing fact-application stream finishes. This is not just a missing implementation detail: the existing completion contracts require a different outcome.

   In the revised test-9 schedule, let v1 normalize C and create its pending application before v2's claims-mode reconcile retires C. When v1's entity flush runs, the new currency guard must suppress application. `FactApplicationCatalog.admit_head` selects the oldest admitted application with `applied_at IS NULL`, irrespective of currency (`src/rememberstack/spine/fact_applications.py:429–441`). `FactAdjudicator.drain` loops until prepare finds no head, and a returned result must contain a real `fact_id` (`src/rememberstack/spine/fact_adjudication.py:287–332`). Returning without applying C either selects the same head forever or, if prepare filters it out, leaves the version's exact application barrier incomplete. `version_applications_ready_on` requires every accepted output's application to have `applied_at` (`src/rememberstack/spine/fact_applications.py:557–569`); `complete_entity_obs_flush` uses that predicate before opening supersession/reconcile (`src/rememberstack/spine/work_ledger.py:485–492`, :1321–1333).

   There is a second membership problem when a claim is already retired at facts admission: `_VERSION_APPLICATIONS` still enumerates every occurrence, and `register_version_applications_on` rejects a missing normalization receipt/application before the entity fan-out can take its empty path (`fact_applications.py:500–550`; `work_ledger.py:1121–1148`). Calling the reduced set “the D88 expected set” does not reconcile this separate D118 expected set.

   **Fix:** define one explicit eligibility/completion contract across normalization, version application registration, canonical-head admission, application receipts, staging retirement, D90 empty completion and readiness. A suppressed application needs a durable, distinguishable terminal outcome that contributes no fact/evidence and lets the stream and barriers finish; it cannot masquerade as a successful fact result or remain an unapplied head. Preserve the frozen normalization output. Update the affected binding E3/application contracts and delivery scope. Extend test 9 to assert that the canonical head advances, the exact application barrier closes, the facts gap disappears and a later application on the same entity runs, including an all-retired expected set. The no-configuration path must retain today's predicates and receipts.

2. **P1 must fix — Deletion can restore testimony whose fact work was suppressed after entry, but reopening only discharged gaps cannot restore its missing facts.** Location: `plan/designs/processing_layers_design.md:219–225`, :279–285, :303–305, :337–341, :380–383.

   The round-2 deletion repair covers an older version that never entered facts. It misses a version that entered, then legitimately contributed nothing under the new currency rule:

   - Living v1 carries C and enters a facts backfill.
   - v2 removes C; its claims-mode reconcile retires C before v1 applies it.
   - v1 suppresses C as §4.3 requires, finishes its remaining facts work and full reconcile, and deletes its entered facts gap at the frontier. v2 subsequently finishes.
   - Delete v2. The engine repoints the lineage to v1 and restores C's currency.

   Restoration is real existing behavior: `DeletionService.delete_version` calls `regained_by_current_version` and runs the resulting positive transitions through the cascade (`src/rememberstack/workers/reconcile.py:576–594`; `src/rememberstack/spine/lifecycle.py:259–289`, :1017–1030). That cascade recounts existing facts; it does not normalize or apply missing facts. Advance step 2 only reopens *discharged* gaps. v1's gap was deleted after successful entered work, so there is no target to advance and no work to apply the now-current C. The version can remain ready with its facts permanently missing. Merely replaying the already-succeeded claim/flush work also does not work under the existing idempotency keys.

   **Fix:** make regained currency reconsider applications suppressed for non-current testimony, including versions already past their facts frontier. Specify a reversible/durable suppression outcome and how repointing reactivates that work and its coverage/readiness dependency without resetting unrelated succeeded work. Reuse the stored normalization products and existing chunks/claim IDs; do not re-extract or re-embed unchanged content. Add the sequence above, distinct from the existing discharged-gap test, and repeat it across an off/on cycle.

3. **P1 must fix — Checking only the incoming claim does not prevent a decision from creating a new fact from a different retired assertion.** Location: `plan/designs/processing_layers_design.md:209–225` (§4.3), especially :219–224.

   The stated conclusion, “Retired testimony therefore never becomes a fact,” is stronger than the incoming-claim check. A fact decision can create several facts using other supplied original assertions and move their support. The application snapshot supplies assertions and claims already supporting candidate facts without filtering out retired testimony (`src/rememberstack/spine/fact_application_inputs.py:239–288`, :316–340). Scope validation verifies that a new fact's source assertion was supplied, but does not require its claim to be current (`src/rememberstack/core/fact_application.py:65–80`). `apply_fact_decision` derives each new fact from `new.assertion_application_id`, which need not be the incoming application (`src/rememberstack/spine/apply_fact_decision.py:101–146`).

   For example, after a claims-mode reconcile retired C_old and settled its old fact, an application from current C_new on the same entity can pass the proposed guard while a valid decision creates N_new from its incoming assertion and N_old from C_old's supplied assertion, moving the latter's support to N_old. Multiple new handles assigned by support moves are allowed (`src/rememberstack/model/fact_application.py:94–116`). N_old can inherit C_old's open window, have zero current support after recount, and never receive a new retirement transition. The later full reconcile still scopes ordinary closure to its own currency transitions (`src/rememberstack/workers/reconcile.py:122–188`), so the original late zero-support-fact problem remains possible, including after a connector cycle already finalized.

   **Fix:** apply the configured-deployment eligibility rule to every source assertion used to create a new fact, revalidated under the already-held participant claim locks, not solely to the incoming application. Specify the treatment of a prepared decision whose supplementary source became ineligible. If historical-only splitting is intentionally allowed instead, define its deterministic settlement and narrow the “never” promise accordingly. Add a fake decision with a current incoming claim and a retired supplementary assertion; assert that it cannot leave a newly open zero-support fact. Preserve unconfigured semantics.

4. **P1 must fix — Advancing at grounding can report a successor ready while its reused claims have never been embedded.** Location: `plan/designs/processing_layers_design.md:237–269` (§4.5), :279–285, :361–371.

   Separating the extraction reuse frontier from readiness is reasonable, but the existing claim embed handler assumes that reused claims' origin versions already completed embedding. It does not embed by occurrence: `claims_for_embedding` filters `claims.chunk_id = ANY(:chunk_ids)` using the origin chunk only (`src/rememberstack/spine/claim_catalog.py:280–299`, :560–572). `EmbedClaimsHandler` takes the current version's chunk IDs and succeeds immediately when that query is empty (`src/rememberstack/workers/p1.py:99–113`).

   A concrete schedule: ingest snapshot v1 with claims off; enable claims with facts still off; backfill v1 through grounding, then pause its `embed_claim`. Advance now admits a newly ingested v2, whose unchanged chunks reuse v1's C. v2's embed job skips C because its origin is in v1, and its claims reconcile succeeds. All eight of v2's expected stages can now succeed even though C has no vector. If v1's embed job dead-letters, v2 remains ready and C remains absent from semantic retrieval. A v2 measured under the newly enabled claims profile can also get a successful profile-complete receipt: existing readiness and metering inspect v2's own stage rows, not the inherited embedding dependency (`src/rememberstack/spine/readiness.py:229–263`; `src/rememberstack/spine/managed_metering.py:358–388`).

   **Fix:** specify how readiness and measured-profile completeness account for embeddings inherited through reused claim IDs. Either wait for the relevant predecessor embedding tail before releasing dependent completion, or make embedding completion occurrence-aware with ownership/deduplication that preserves one paid embedding per unchanged claim. A plain occurrence-based scan without coordination could introduce duplicate paid calls. Test v2 while v1's embed is pending and then dead-lettered, and verify recovery fills C exactly once. Keep the unconfigured stage list and default predicates unchanged.

5. **P1 must fix — `combined_context(layers={facts})` is admitted but has no permitted construction.** Location: `plan/designs/processing_layers_design.md:403–405`, :419–440, :468–477; `plan/designs/open_query_space_design.md:405–415`.

   The selection is any non-empty subset. `combined_context` has sources, claims and facts as alternative channels, so a facts-only request retains a channel and passes §7.2. The design permits only the *fact* child to be synthetic, and `ContextBundleV2` requires both children with exact evidence/fact grains (`src/rememberstack/model/envelope.py:679–695`). The same contradiction applies to an MCP session narrowed to facts: the bundle tool remains applicable but cannot produce its contracted result.

   **Fix:** define the symmetric synthetic empty evidence-grain `boundary` child when neither sources nor claims is admitted, with its temporal scope, freshness and truncation rules, and reconcile D87/D114's refinement notes. Alternatively explicitly reject this selection for the bundle, before any read, and document that narrower contract. The symmetric construction best matches the stated any-subset channel rule and requires no schema, tool-version or manifest change. Add acceptance cases for every non-empty subset, especially facts only.

6. **P2 should fix — Originating-lane propagation must account for the entity-global application stream, not just the current worker's lane.** Location: `plan/designs/processing_layers_design.md:350–359` (§5.5); `plan/designs/orchestration_design.md:107–122`; acceptance test 10.

   If backfill A and fresh steady B mention the same entity, B's worker can apply A's earlier pending application. Attributing its model call and repair to B's worker lane charges backfill work to steady and can run its label repair even with the backfill label budget exhausted. This is not D67 promotion of the same work row: the version-scoped flush units and distinct applications need not share an idempotency key.

   **Fix:** define what owns an application's originating lane when a different unit drains it, how that provenance reaches metering/follow-ups, and what happens when the canonical head's own route budget is exhausted. Distinguish queue priority from unavoidable sharing of the entity stream and its locks; the current “never delays fresh ingestion” statement is too absolute. Extend test 10 with concurrent steady work on the same entity, using distinct claims/applications and no duplicate promotion. Do not rely solely on plumbing the claiming worker's lane.

7. **P2 should fix — The gap schema cannot store the lane that admission is required to preserve.** Location: `plan/designs/processing_layers_design.md:89–103`, :164–165, :317–321; `plan/designs/postgres_schema_design.md:384–397`.
