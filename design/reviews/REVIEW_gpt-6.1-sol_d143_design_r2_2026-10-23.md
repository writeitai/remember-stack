1. **P1 must fix — Drain does not resolve the gapless-predecessor admission race (round-1 finding 3 remains).** Location: plan/designs/processing_layers_design.md:149–156, :189–197, :253–262.

   Boundary admission still asks only whether an earlier version has an open gap, whereas Advance asks whether earlier source-complete versions actually completed the layer. Draining changes how long unfinished work lasts; it does not make these predicates equivalent.

   A valid schedule is: v1 enters claims with claims enabled; claims are switched off before its Selection/Claimify work finishes; the reduced readiness contract makes v1 source-ready, allowing the caller to submit v2; claims are switched on again before v2 completes embed_chunk. Neither version has a claims gap yet. Setup seeds nothing, and v2's boundary admits it while v1 is still draining. If v1 has not published the reusable products, v2 pays for unchanged sections. SelectionCatalog.prior only reads smaller version numbers (src/rememberstack/spine/selection_catalog.py:113–149); Claimify reuse has the same restriction (src/rememberstack/spine/claim_catalog.py:386–406). v1 cannot subsequently reuse the products v2 produced. A dead-lettered predecessor makes the distinction still more important.

   **Fix:** use the actual predecessor-completion predicate at both boundary admission and Advance for deployments/lineages participating in layer switching, including gapless entered work. Preserve the untouched no-configuration path explicitly. A deferred boundary must also participate in the wake-up protocol in finding 3. Add an off/on test where v2 crosses its boundary before a gapless v1 publishes Selection and Claimify, and assert provider-call counts and claim-ID reuse for untouched sections.

2. **P1 must fix — The living supersession guard misses the interval before the current version reaches its claims boundary.** Location: plan/designs/processing_layers_design.md:181–187; plan/designs/evidence_lifecycle_design.md:319–322.

   An open claims gap is not a reliable test for “the current version's occurrence set is incomplete.” E0 makes a structured version current before its chunk/embed/extract work finishes: see _MARK_VERSION_READY and _MARK_LINEAGE_CURRENT in src/rememberstack/spine/document_catalog.py:1186–1227. Gaps are created only at the later embed_chunk boundary.

   During a claims backfill of living v1, let v2 finish structure and become current, then pause it before embed_chunk completion. v1's claims-mode reconcile now sees v2 as current but finds no v2 claims gap, so the proposed guard allows supersession. The actual stale query retires v1 claims absent from v2's occurrence set (src/rememberstack/spine/lifecycle.py:932–945). When v2 subsequently reuses unchanged chunks, attach_reused_claims only attaches occurrence links; it does not restore testimony currency (src/rememberstack/spine/claim_catalog.py:116–201, :460–473). The backfill can therefore finish with unchanged, reused claim IDs permanently non-current.

   **Fix:** in the layer-managed/backfill case, guard supersession on actual completion of the current version's claim occurrence set, covering its pre-boundary interval as well as an entered/unentered gap. Coordinate the check with current-version changes and occurrence publication; an isolated unlocked gap lookup is insufficient. Scope the new guard so the required unconfigured all-on behavior remains unchanged. Test by pausing v2 between structure and embed_chunk, running v1's reconcile, then completing v2 and asserting currency as well as reuse.

3. **P1 must fix — A living lineage can lose its only wake-up when its current version is not source-complete at seeding time.** Location: plan/designs/processing_layers_design.md:149–152, :256–278, :289–293.

   Consider claims-off living v1 with a completed sources layer and an unentered claims gap. v2 becomes current after structure, but its chunk/embed work is still running. Claims are enabled now. Setup finds v1's gap, but the current-only policy selects v2, which has neither completed sources nor acquired a gap. It cannot yet be entered. When v2 later completes embed_chunk, the boundary's earlier-gap rule defers it behind v1 and records v2's gap. The design names setup, layer completion and deletion as the drivers of Advance; neither version has claims work that can complete, v1 is forbidden as a living backfill target, and setup has already finished. The lineage can remain backfilling forever.

   There is a related ordering ambiguity even when the current version is source-complete: Advance requires earlier versions to be complete or discharged, but §5.3 associates discharging their unentered gaps with entering the current version. The protocol must say when these obsolete blockers are discharged relative to admission.

   **Fix:** make recording a deferred gap/source-boundary completion invoke the same lineage advancement procedure in that transaction. For living lineages, explicitly discharge superseded unentered gaps before evaluating the surviving target's predecessor predicate, while retaining genuine entered/draining/dead-letter blockers. Define behavior when the current target is not yet source-complete, is already layer-complete, or has terminal source-stage work. Require the schedule above to finish without another setup run, including a zero-chunk current version. This can remain event-driven; no polling job is necessary.

4. **P1 must fix — “Current version only” at enqueue time does not prevent retired testimony from becoming new facts, and the second reconcile can miss its closure.** Location: plan/designs/processing_layers_design.md:168–179, :276–285; round-1 findings 8 and 10.

   The revised policy fixes the static case of backfilling an already superseded living version, but not supersession while an admitted facts backfill is pending:

   - Facts-off v1 finishes claims, including claim C, and gets a facts gap.
   - Facts are enabled; setup enters v1 in facts, but its normalizer has not run yet.
   - A new living v2 removes C. Its facts boundary defers behind v1's entered facts gap and opens the claims tail. v2's claims-mode reconcile retires C and recounts its affected facts; C has none yet.
   - v1's admitted E3 work now runs on retired C. Its full reconcile subsequently finds no new currency transition.

   The ordinary handlers permit this schedule: normalize fan-out selects all occurrences without a currency predicate (src/rememberstack/spine/work_ledger.py:1793–1805); the normalizer accepts and normalizes C (src/rememberstack/workers/e3.py:255–299); the application snapshot includes the incoming claim irrespective of its currency (src/rememberstack/spine/fact_application_inputs.py:239–288). With no candidates, adjudication can choose a new fact without a model decision (src/rememberstack/spine/fact_adjudication.py:734–742), and application inserts it without a current-testimony guard (src/rememberstack/spine/apply_fact_decision.py:101–146). Its recount correctly produces zero support (:414–427), but does not perform lifecycle closure.

   Reconcile scopes recount and zero-support handling to this run's currency transitions, including recovery only under its own reconciliation_id (src/rememberstack/workers/reconcile.py:122–188). v2's retirement happened in another run before the fact existed. Neither v1's full reconcile nor v2's later full reconcile rediscovers it. A newly created fact can remain unclosed with zero support; an explicit open validity window also makes the retrieval consequence visible. The same late-application problem can occur when already-entered facts work drains after switching facts off. Connector-stamped cases additionally need to account for cycles that have already finalized.

   **Fix:** define eligibility and settlement throughout admitted backfill/drain execution, not only when choosing its version. Either deterministically skip stale incoming testimony, with matching D88/D90 expected-set and empty-completion behavior and application-time revalidation, or guarantee a deterministic final settlement of every fact touched by the admitted work even when its currency transition occurred in another completed reconcile. The latter must preserve the declared history policy and handle finalized/LOSSY cycles. Add the schedule above with a fake normalizer yielding an open-window fact, checking provider calls, final currency, support and closure. The assertion that no cross-run settlement is needed is currently too strong.

5. **P1 must fix — Discharged gaps cannot recover when deletion makes their version current again.** Location: plan/designs/processing_layers_design.md:209–213, :256–280, :329–336.

   With claims off, ingest living v1 and v2. Enable claims and finish the current-only backfill of v2; v1's claims/facts gaps are discharged and its missing stages report skipped. Delete v2 through the existing version-deletion grain. Deletion repoints current_version_id to the newest surviving ready version, v1 (src/rememberstack/spine/lifecycle.py:1285–1297). Its restoration code can restore only claims already occurring on that version (src/rememberstack/workers/reconcile.py:561–595). v1 was never extracted.

   The proposed deletion hook deletes v2's gaps and invokes Advance, but v1 has no open gap: discharged_at excludes it. There is no work to restore its missing layer, coverage says complete, and readiness continues to report skipped for the now-current version. This is a new consequence of discharge, rather than the ordinary deleted-head case covered by test 8.

   **Fix:** make current-version repointing reconsider discharged coverage in the same deletion-compatible transaction. Reopen the newly current version's missing layers and advance them in dependency order, and specify how its paid products are restored/reused. Simply rerunning E1/E2 is not an adequate reuse policy: the existing lookups only use earlier versions and deliberately exclude deleted testimony. Preserve chunk embeddings and identities, and explicitly resolve claim reuse/restoration for this backward move. Test current-version deletion after both claims and facts discharge, including repetition after another off/on cycle.

6. **P1 must fix — Ordinary fact handlers send backfill follow-ups to the steady lane, bypassing the promised backfill budget.** Location: plan/designs/processing_layers_design.md:264–266, :295–299; plan/designs/orchestration_design.md:108–122.

   Entering the initial E3 work on the backfill lane does not keep the resulting work there. Every fact application can enqueue its own projection repair: src/rememberstack/spine/apply_fact_decision.py:431–451 calls enqueue_fact_projection_repair, which hard-codes label_relation to ProcessingLane.STEADY (:513–525). These are fact_application-targeted jobs, separate from the version-targeted label job opened by the full reconcile. They embed facts and refresh profiles (src/rememberstack/workers/p1.py:175–184, :284–315), so this is paid work, not just a notification. Window-review requests likewise currently hard-code steady (src/rememberstack/spine/period_adjudication.py:543–555).

   A large facts backfill therefore creates paid steady-route work even when the operator's label_relation backfill budget is zero. It can consume the fresh-ingestion budget and queue capacity. The design's separate-budget claim is not true if it reuses these ordinary APIs unchanged.

   **Fix:** propagate the originating lane through application/projection-repair APIs and backfill-caused review requests, retaining steady as the ordinary-path default and D67's promotion rule for work also required by steady ingestion. Identify all non-version-targeted follow-ups in the contract and delivery plan. Test a facts backfill with zero backfill follow-up budget and available steady budget: its repairs must remain parked on backfill, with no steady-attributed provider calls. This needs no extraction/embedding identity change.

7. **P2 should fix — Distinguish a reuse/advancement frontier from full readiness and measured-profile completion.** Location: plan/designs/processing_layers_design.md:37–38, :199–230, :238–243.

   The document defines a layer as complete when its work finished, then defines claims completion as grounding and facts completion as full reconcile. Both definitions omit paid tail work: embed_claim can still be pending, and full reconcile enqueues label_relation rather than waiting for it. Those early points can be useful for advancing reuse, but §4.5 also uses “complete in every layer” to define the measured receipt.

   Today's managed success waits for the exact readiness stage list, including claim embedding and labeling; it also reports terminal tail failures (src/rememberstack/spine/managed_metering.py:358–408; src/rememberstack/profiles/selfhost.py:1706–1723). Replacing that with §5.1's frontier would permit a standard-profile success before labeling, or even before a later label dead letter, contrary to the default-receipt promise. The new measured-profile pin correctly addresses round-1 finding 11; it still needs an unambiguous completion predicate.

   **Fix:** name the early points as advancement/reuse frontiers and define profile completeness separately using every stage required by the immutable measured profile. For the standard profile retain today's twelve-stage predicate and completion timestamp; the claims profile must include embed_claim and its reconcile. Add tests with full reconcile succeeded while embed_claim/label_relation is pending and then dead-lettered. Keep serving readiness and coverage terminology consistent with these distinctions.

Other checked scope and tradeoffs:

The claims tail/full-reconcile split by component version is compatible with ledger idempotency: the new claims mode can run independently, while the all-on reconcile generation remains unchanged. Retaining deterministic recount/closure, review flags, evidence_changed and the deleted-testimony cascade addresses the old facts-on → off counting failure. It does not by itself settle facts created after those currency transitions, as finding 4 shows.

Profile refresh while facts are off is an explicit cost exception in this revision, not zero-cost maintenance. Reconcile calls refresh_for_facts (src/rememberstack/workers/reconcile.py:215–222), EntityProfileRefresher can embed changed profile inputs (src/rememberstack/spine/profile_refresher.py:100–116, :250–277), and self-host composition supplies ConvergingProfileRefresher, which can run identity convergence (src/rememberstack/spine/profile_convergence.py:57–96). That exception should be included in off/on provider-count and budget fixtures. It does not require re-embedding unchanged source chunks, and is already acknowledged in analysis §5.1; it must not be described as a guarantee of no fact-related provider work after every switch-off.

The retrieval channel/dependency split is now coherent, including entity-scoped claims_and_sources_context and bound sandbox claim filters. ContextBundleV2 still requires both children with exact evidence/fact grains (src/rememberstack/model/envelope.py:679–695); disabled-side disclosure can fit that schema, subject to finding 8. D140 scope_pending probes must use the admitted channels, as §7.2 and test 5 now require; the current implementation's unconditional four probes are at src/rememberstack/surfaces/query_engine.py:1750–1761. Keeping sandbox layer metadata outside the manifest avoids a hash change.
