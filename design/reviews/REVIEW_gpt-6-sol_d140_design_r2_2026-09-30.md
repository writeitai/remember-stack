## P1

1. **`plan/designs/effective_time_and_section_references_design.md:157-165` — keyed ingest can violate version identity and lose publisher edition keys.** On `main`, `DocumentCatalog.record_upload` creates a new version for A→B→A (`src/rememberstack/spine/document_catalog.py:73-82,160-165`), but D140 says an ingest carrying A's old `version_key` and bytes after B is an idempotent observation of A. It would attach a new effective period to the old observation and skip the new version. Conversely, when two adjacent publisher editions have identical bytes but distinct keys, the D55 byte no-op cannot set the second key because `:160` permits a key only at creation; a static reference to that edition is unaddressable. **Fix:** make the ingest decision and key conflict rules explicit for both cases. Preserve A→B→A as a new observation; either create separate same-byte versions for distinct declared edition keys or model immutable key aliases with unambiguous pinned resolution. An old key used on a later observation should reject or use the period API, not silently select an older version.

2. **`plan/designs/effective_time_and_section_references_design.md:391-418` — text-origin reuse gives an older back-filled edition a future assertion date.** The design expressly allows out-of-order version arrival (`:141`). If a 2026 edition is ingested first and an otherwise identical 2024 edition later, step 2 copies the 2026 chunk's `text_origin_at` into the 2024 chunk. E2 then reuses claims interpreted against 2026 (or stamps a fresh extraction with 2026), despite the older source's 2024 date. The earliest existing *ingested* match is not necessarily the earliest source-dated text. **Fix:** require an eligible match's origin date to be no later than the incoming version's source date; otherwise use the incoming date and re-extract. State the conservative behavior for missing/uncertain dates and for claims already extracted before a backfill, rather than claiming the stored date proves when words were first written.

3. **`plan/designs/effective_time_and_section_references_design.md:291-303` — `search_documents` has no coherent result grain when the scope selects several versions.** `:246-248` deliberately selects both concurrent versions; `overlap` and `history` select multiple editions routinely. Yet the existing D134 contract returns one result per lineage judged by one version (`document_metadata_and_search_design.md:122-128`; `src/remember/models.py:225-240`). D140 says `versions: current` judges “each selected version” and `versions: all` judges “every version the scope selects,” leaving them equivalent and leaving no rule for which version's metadata, hit, `effective` period and handle are returned or how they page. **Fix:** define either a version-grain result with version-aware rank/order/cursor, or a lineage-grain result with a deterministic selected representative plus every matching edition's version-addressed handle and interval. Define the meaning of both `versions` settings under each time mode.

4. **`plan/designs/effective_time_and_section_references_design.md:674-680` — the fact evidence gate is not guaranteed before top-k nomination.** The text places the gate in the fact read over a “bounded candidate set,” while the existing `facts_context` first nominates/ranks candidates and then confirms/hydrates them (`src/rememberstack/surfaces/query_engine.py:746-819`). If the top candidates are supported only by future editions, filtering those results can return empty despite a lower-ranked, in-force fact. The binding retrieval rule forbids global top-k followed by scope filtering (`decisions.md:3768-3774`). **Fix:** make in-scope support a nomination and confirmation eligibility predicate before each relevance bound, or specify a complete refill strategy that preserves the same ranking and work budget; only then hydrate gated evidence.

5. **`plan/designs/effective_time_and_section_references_design.md:603-615` — a supplied reference set cannot be restored after replacement.** The table permits only one row per `(deployment_id, version_id, set_hash)` (`:446`), and a same-hash PUT is a no-op (`:604-605`). After A is materialized, B supersedes it, and the caller PUTs A again, the no-op leaves B live; inserting a new A generation violates the unique constraint. This breaks correction/replay of caller-supplied links. **Fix:** distinguish idempotent retry of the *active* set from reactivation of a superseded set. Give each activation a generation identity (or atomically reactivate the old row and its retained crossrefs) and define worker idempotency and visibility for A→B→A.

6. **`plan/designs/effective_time_and_section_references_design.md:545-558` — target resolution can report an unreadable version as `resolved`.** The temporal join uses every target in-force interval, while §3.2 (`:239-241`) excludes a version until it and its current representation are ready. A target edition still converting can therefore be returned with a target representation, section title and first chunk ids that do not exist. Pinned targets have the same missing readiness rule. **Fix:** join target readiness/current representation before emitting `resolved`; return a distinct processing/unavailable status when the selected target is pending, without falling back to an out-of-force predecessor. Apply this consistently to point and range joins.

7. **`plan/designs/effective_time_and_section_references_design.md:628-632` — extracted reference identity is insufficient for version-grain rows and D65 reprocessing.** Keying extracted rows on `(version content, crossreferencer version)` collides across A→B→A: the third version shares A's content hash but needs its own `from_version_id` rows. The table also stores representation-relative `from_char_start/end` (`:458-459`) without a `from_representation_id`. D65 can swap a version's current representation after a converter upgrade (`media_design.md:465-486`), leaving old coordinates exposed or duplicate extraction generations live. **Fix:** key extraction by source `version_id`, representation/generation and crossreferencer version; store the representation coordinate and select only the active generation, with an atomic swap on successful reprocessing.

8. **`plan/designs/effective_time_and_section_references_design.md:175-178` — `clear_effective_time` breaks the promised belief-pinned view.** Period declarations have `declared_at`/`retracted_at`, but `documents.effective_time` is a single mutable flag. After a caller clears the lineage, `versions_in_scope(... believed_at=B)` sees `undeclared` now and picks the served version even if it uses B before the clear and the declaration ledger still reconstructs the old intervals. A paged read pinned at B can therefore move rows across pages, contrary to `:300-309`; historical-belief graph reads have the same discrepancy. **Fix:** record mode transitions in the same ledger and evaluate periodised/undeclared state at `believed_at`, or explicitly snapshot the selected version set in cursors and narrow the stated belief-time contract. Include clear/redeclare in correction and paging tests.

## P2

1. **`plan/designs/effective_time_and_section_references_design.md:353-369` — historical section absence can be falsely reported as repeal.** Existing versions are not restructured, and the migration backfills only hashes (`plan/plans/effective_time_and_section_references.md:27-35`). Their pre-D140 headings may contain `{#key}` but stored sections have `section_key = NULL`. `section_history` currently emits `absent` whenever a selected version lacks the key (`effective_time_and_section_references_design.md:583-589`), so an old provision appears removed rather than unindexed. **Fix:** deterministically backfill keys from stored heading/block data where possible, or return a separate unknown/not-indexed status for pre-parser representations.

2. **`plan/designs/effective_time_and_section_references_design.md:687-689` — the published fact-scope predicate cannot honor a separate belief instant.** `fact_in_scope_support` takes `evaluated_at` but no `believed_at`, although `versions_in_scope` takes both (`:250-253`) and graph helpers accept a separate belief time. A query-space caller cannot reproduce the operation's evidence set for declarations corrected after that belief instant; PR #486 changes fact-window reads, not this missing declaration clock. **Fix:** add `believed_at` to the predicate and manifest signature and define the default and forwarding rule from graph/query-space calls.

3. **`plan/designs/effective_time_and_section_references_design.md:131-135,324-326` — the scale claim has no bounded query plan.** `effective_intervals(deployment_id, believed_at)` derives a window over *every* declaration in the deployment, while every scoped search invokes `versions_in_scope`; the cost section calls this “one indexed predicate over a small per-lineage period set.” At millions of documents the declared function has no lineage/candidate restriction or indexed current-time access path, and window derivation cannot use the stated per-lineage index as a global selective predicate. **Fix:** specify how each read reaches candidate lineages/versions before period derivation without dropping valid ranked results, plus the supporting indexes or maintained projection, and state a corpus-scale verification target.

4. **`plan/designs/effective_time_and_section_references_design.md:596-605` — sets above 64 MiB have no ingestion path.** The size cap is a reasonable per-request bound, but the only write operation is full-set replacement and rejects a larger version's set with `413`; the design targets millions of references and provides no staged/chunked complete-set protocol. **Fix:** define a bounded multipart staging/finalization route with a single E0 materialization generation, or justify a measured per-version maximum that makes the cap a true scope boundary.

5. **`plan/designs/postgres_schema_design.md:1150-1162,1178-1179` — schema comments retain the pre-D140 assertion-time rule.** They still say `source_modified_at` directly feeds derived claims' `asserted_at`, while D140 uses `chunks.text_origin_at` for fresh claims and may inherit an earlier version's date. A cold reader of the binding schema gets a contradictory rule. **Fix:** amend those comments to describe the source-time fallback and the recorded chunk date as the E2 input.

## Nits

1. **`plan/designs/postgres_schema_design.md:1463-1467` — non-`amends` rows can still carry `change_effective_from`.** The CHECKs constrain the date when `change_date_known` is true or false, but permit a non-amendment with a NULL flag and non-NULL date. **Fix:** require `change_effective_from IS NULL` whenever `kind <> 'amends'`.
