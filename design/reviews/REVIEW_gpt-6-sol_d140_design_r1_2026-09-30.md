# D140 design review

Compared `origin/main...HEAD` at merge base `1dc23f21` and checked the affected implementation, schema, and binding designs on `origin/main`. This is a design review; no runtime behavior in this PR was treated as shipped.

## P0

None.

## P1

1. **`plan/designs/effective_time_and_section_references_design.md:160` — `current_version_id` is described incorrectly, and the proposed document handle can open the wrong edition.** On `main`, `DocumentCatalog` moves the pointer only after a representation becomes ready (`src/rememberstack/spine/document_catalog.py:642-666`); `document_inventory.py:11-17` explicitly distinguishes the newest observed version from the served one. Correct D140, D55's new refinement at `decisions.md:1809`, and `evidence_lifecycle_design.md:132`. More consequentially, `search_documents` returns a lineage P3 path (`src/remember/models.py:225-240`): a result judged against the edition in force on date T can hand the agent a path that opens a different, newer served edition. Specify version-addressed access for every scoped result (including P3/source handles), or make those paths honor the selected version.

2. **`plan/designs/effective_time_and_section_references_design.md:353` — pinned references use a mutable cursor as version identity.** `source_version_ref` advances on an identical-byte ingest (`src/rememberstack/spine/document_catalog.py:203-215,808-813`), and D55 calls it a connector-efficiency cursor (`decisions.md:1819-1825`). It is nullable and has no uniqueness constraint (`p0_02_0003_entities_evaluation_e0_e1.py:363-385`). A previously pinned link can cease to resolve or bind ambiguously after ordinary polling. Give target versions an immutable, unique address (for example an immutable caller version key or lineage plus content hash), preserve the mutable cursor separately, and define late binding and deletion against that address.

3. **`plan/designs/effective_time_and_section_references_design.md:391` — floating target resolution is undefined for `overlap` and `history`, and for intentionally overlapping effective periods.** Those scopes select intervals or several versions, not one “reading instant”; §2.2 explicitly permits two editions in force simultaneously. A single target version/status in `document_references` cannot represent a reference that floats across a target amendment within the requested range. Define a temporal join between source and target intervals, the returned multiplicity/intersection periods, ordering and limits; for a point query with multiple targets, return the ambiguity rather than choosing one silently. Also say whether `chunk_id` pins its source version when no `time` is supplied (`:401-405`).

4. **`plan/designs/effective_time_and_section_references_design.md:474` — the default fact answer can still present future or repealed text as current law.** Snapshot-mode claims from *all* versions remain current testimony (§2.4; D54 at `decisions.md:1746-1769`). §8 only says E3 *may* use a period to bound a D118 fact window, while `plan/plans/effective_time_and_section_references.md:15` ships that input separately from temporal text retrieval. Thus `facts_context`/`combined_context` can keep returning a fact supported solely by a future edition even when chunk search correctly excludes it. Specify a deterministic current/at eligibility rule or required adjudication constraint for periodised evidence, its treatment of conflicting claim-valid dates, and a delivery dependency that prevents this inconsistent default answer. Keep D118 as the fact-window authority; PR #486's belief-time rule does not repair this eligibility gap.

5. **`plan/designs/effective_time_and_section_references_design.md:242` — a time-selected reused claim can cite the wrong version and span.** The design selects a claim by a `chunk_claims` occurrence in the chosen version, but `search_claims` on `main` confirms and returns the claim's *origin* chunk/span (`src/rememberstack/surfaces/query_engine.py:2981-3019,4400-4419`). D56 reuse deliberately shares one immutable claim across version chunks. A query `at T` could therefore return edition 2's period alongside edition 1's `chunk_id` and coordinates; after origin deletion, that citation may be unreadable. Specify selection and hydration of a surviving occurrence in the selected version/representation, including its per-occurrence spans, and make `effective` describe that occurrence rather than the origin claim row.

6. **`plan/designs/effective_time_and_section_references_design.md:70` — the new tables do not enforce their stated lineage/version ownership.** Separate `(deployment_id, doc_id)` and `(deployment_id, version_id)` FKs allow a period for doc A to name a version of doc B. The same defect affects `document_crossrefs.from_doc_id/from_version_id` (`:369-372`) and `document_reference_sets.doc_id/version_id` (`plan/designs/postgres_schema_design.md:1467-1468`); a supplied row can also name a reference set of another version. The existing `document_versions` schema already has `UNIQUE (deployment_id, doc_id, version_id)` for this invariant (`p0_02_0003_entities_evaluation_e0_e1.py:380-394`). Use composite ownership FKs and a composite reference-set FK, with tenant and version validation on the write path.

7. **`plan/designs/effective_time_and_section_references_design.md:490` — deletion is specified as a cascade, but D135 deletes by soft tombstone.** `src/rememberstack/spine/lifecycle.py:1224-1244` updates `deleted_at` and repoints the served version; it does not delete `document_versions`, so the new `ON DELETE CASCADE` FKs will not remove periods, reference sets, or outgoing references. Target `ON DELETE SET NULL` will not run either. Specify the D135 worker's explicit updates and visibility rules for version versus lineage deletion, plus D74 hard-forget artifact scrubbing. Reconcile “every past declaration stays readable” (§2.1) with §9's promise to remove periods.

8. **`plan/designs/effective_time_and_section_references_design.md:46` — retracting the last live period reclassifies a lineage as undated and can resurrect withdrawn text.** §3.2 falls back to `current_version_id` whenever no *live* declaration remains. A `set_effective_periods(..., [])` correction on the only dated version therefore makes `current` return that version again, even though it was not in force. Preserve an explicit periodised-lineage state after declarations are retracted, or forbid clearing the last period without an explicit mode change and define that change's semantics.

9. **`plan/designs/effective_time_and_section_references_design.md:304` — text-origin reuse is not a reproducible, indexed identity as specified.** Only `text_origin_at` is added to `chunks`; there is no stored/indexed date-free key for the “look up the earliest” operation across millions of chunks. The propagation rule can also retain a timestamp from a deleted origin via a surviving chunk, contradicting “earliest live” and the claim that replay derives it from immutable live inputs (`:309-324`). Define the indexed identity, deterministic tie/order rule, parser/representation generation boundary, and what happens to descendant chunks and reused claims when the origin version is deleted. The current E1 key uses both `source_modified_at` and `published_at` (`src/rememberstack/workers/e1.py:629-660`), so specify exactly which facts are replaced.

10. **`plan/designs/effective_time_and_section_references_design.md:313` — the proposed E2 date and the claim's assertion clock diverge.** The rule changes E2's header and `extraction_input_hash` to `text_origin_at`, but the plan does not change claim creation, which still sets `asserted_at = source.source_modified_at or source.published_at` (`src/rememberstack/workers/e2.py:1293-1296`); E2's header is also currently built from `ChunkSource` (`:1741-1749`). A new extraction after a parser/extractor bump would interpret “last year” against the old date yet stamp the claim with the new date. Define one per-chunk date passed through E2 header, extraction, and assertion timestamp, and explain how that refines D55's source-time testimony rule.

11. **`plan/designs/effective_time_and_section_references_design.md:280` — `section_history.changed` can miss a changed provision.** The hash excludes children, while the heading parser's parent section span includes them (`src/rememberstack/core/structure_skeleton.py:111-118`). A paragraph nested below `{#par_5}` can change without changing §5's own-block hash, yielding `changed = false` for a provision whose text differs. Store a subtree hash for the “did this section change” answer (and optionally a separate own-block hash), or explicitly restrict `changed` to the direct body and expose descendant changes. Define effective-time ordering and absence rows as well: `version_no` is ingest order, and a missing key may mean a repealed section rather than a harmless skipped row (`:413-417`).

12. **`plan/designs/effective_time_and_section_references_design.md:82` — the restored-by-identical-bytes example assumes an ingest behavior `main` cannot perform.** `DocumentCatalog` says A→B→A creates a new version (`src/rememberstack/spine/document_catalog.py:73-82,160-194`), yet `document_versions` has `UNIQUE (deployment_id, doc_id, content_hash)` (`p0_02_0003_entities_evaluation_e0_e1.py:380`), so that insert conflicts. D140 instead asserts that identical bytes in one lineage are always one version. Resolve the existing schema/catalog discrepancy in the design and state whether reversion reuses a version with another period or creates another version sharing one content object; then align period, citation, and testimony semantics.

## P2

1. **`plan/designs/effective_time_and_section_references_design.md:96` — readiness rules contradict the shown view and promise an unavailable freshness signal.** The prose says the period view includes only ready versions; its SQL filters only deleted versions. §3.2 then correctly says pending versions must participate in end derivation but not selection. Separate the declaration/derivation view from ready-version selection in the contract. `Freshness` on `main` has only timestamps and K/P1 fields (`src/remember/models.py:533-539`), so specify the result field/query that will actually name a pending lineage as promised at `:203-209`.

2. **`plan/designs/effective_time_and_section_references_design.md:235` — `search_documents(time=at T, versions=all)` silently discards the requested temporal restriction.** §3.4 and `document_metadata_and_search_design.md:129-135` say `versions=all` judges every version, including future or undated versions of a periodised lineage. Define these options as incompatible with validation, or make `versions=all` mean all versions *within* the requested scope and introduce a separately named unscoped audit option. Also reconcile filter-only pagination's pinned `as_of` with effective-period corrections between pages (`document_metadata_and_search_design.md:146-151`).

3. **`plan/designs/effective_time_and_section_references_design.md:401` — reference retrieval is capped without a way to exhaust a large incoming set.** `k <= 200` and the proposed `(to_doc_id, to_section_key)` index do not provide a cursor, stable order, or bounded temporal/source-version filtering for millions of references. Add keyset pagination and a deterministic order with the scope evaluation instant pinned across pages; specify the indexed query shape for incoming section/subtree lookups. The 10,000-row supplied-set call limit at `:423-425` also needs a batching or complete-set replacement protocol for larger versions.

4. **`plan/designs/effective_time_and_section_references_design.md:438` — an invalid source section is silently promoted into a document-level reference.** That loses the supplied fragment provenance and makes incoming/outgoing section queries misleading. Reject the set/item with a location-specific error or retain the supplied key with an explicit unresolved-source-section status; do not broaden the reference's source scope.

5. **`plan/designs/effective_time_and_section_references_design.md:466` — the public reference view and the new operation have different visibility contracts without a specified read path.** `document_crossrefs_live` excludes unresolved targets, while `document_references` promises `target_not_ingested` and `pinned_version_missing` rows. Specify a private, authorization-checked operation query that can read those rows without exposing retained target identity after D74 forget, and define which statuses are allowed when the target was deleted or forgotten.

6. **`plan/plans/effective_time_and_section_references.md:4` — the delivery plan says WP-ET.1–5 and public docs are implemented “this PR”, but #500 changes only design files.** Correct the delivery column and obligations to name subsequent implementation PRs. `:23-25` also calls the migration wholly additive although `section_content_hash text NOT NULL` is added to an existing populated table (`postgres_schema_design.md:1364`); specify backfill/restructure before enforcing non-null, and account for the parser-generation bump forcing one extraction-basis rollover (D56/D65).

7. **`plan/designs/postgres_schema_design.md:1438` — `amends` may omit the effective date despite the kind's definition.** The CHECK only forbids dates for other kinds; it allows `kind='amends', change_effective_from=NULL`. Require a date when the source supplies one and define an explicit unknown-date case if undated amendments are intended, so `section_history` does not imply a known amendment timeline from a null field.

## Nits

1. **`plan/designs/open_query_space_design.md:629` — `from` and `to` are awkward SQL parameter names** (`from` is a SQL keyword). Use `from_at`/`to_at` or `range_start`/`range_end` consistently in the SRF signature and callers.

2. **`plan/designs/effective_time_and_section_references_design.md:327` — “bounded fan-out” does not follow from omitting graph vertices.** The section-reference operation still needs explicit pagination and work bounds, as above; state that rationale directly.

Verdict: Request changes
