## Judgements

- **(a) Eligible-set pushdown: accept the strategy.** _run_testimony enumerates with limit-plus-one inside the same _ranked_connection that subsequently scores exactly or opens the cursor. The predicate relation includes deployment, D140 scope, document metadata and semantic attestation; matching versions and every authority join retain deployment predicates. No tier-selection race or new tenant-isolation hole was found. At ≤5,000 rows, canonical scoring and stable-ID ordering are exact. At 5,001–20,000, membership filtering preserves the BM25 index order and its reconciliation condition; HNSW remains approximate, and its exhaustion count receives the same membership filter. Above 20,000, the bounded loop can disclose an incomplete result. Document-filtered claims always looping is correct with that disclosure. The PostgreSQL tests exercise all three paths by lowering thresholds; the sweep measures around 5,000, not every production threshold boundary.
- **(b) Query-dependent BM25 margin: the old counterexample is fixed; the universal proof is not closed.** The positive-sum gamma approach is appropriate for the inspected float4 index accumulations and the tighter standalone double computation. The new margin is substantially conservative for the 40,000-term case. But n is not bounded by the claimed disjoint-token argument, and the permitted epsilon domain does not justify every reciprocal factor in the written proof. Correct the count/domain and proof rather than calling the entire supported domain proven; R2 P2-1. No new PostgreSQL wrong-ranking counterexample is claimed here.
- **(c) One read context: accept the architecture, request completion.** The shared pool wiring and snapshot lifetime repair most of round 1. Snapshot import does not freeze statement clocks, and carrying a deadline does not make omitted deadlines or outer statements bounded. R2 P1-1/P1-2/P1-3/P1-4 identify the remaining paths. Standalone facts also creates a fresh local database_deadline instead of deriving it from ReadOperation (query_engine.py:1096).
- **(d) ef_search=200: accept as a measured starting setting.** nominate_and_confirm sets it with transaction-local set_config(..., true) before semantic cursor execution and records it in limits (p1_ranked.py:245). It is not restored per cursor; it remains active through the enclosing operation and is restored when the transaction ends/rolls back. That scope is compatible with the contract and does not leak into the next pooled operation. The archived synthetic recall result supports the choice; it is not a latency or real-query recall gate. Put the actual setting and rationale in the binding design, which currently only names ef_search as a reported limit.
- **(e) Full fact authority before nomination cut: accept.** The join is now applied before an accepted candidate consumes depth in both loop and scoped branches. It closes the invalid-head starvation defect without weakening D140 or fact identity. The exact-scan input budget must count the same survivor scope; adding the authority join does not repair that separate defect.
- **Latency: merging is not acceptable under the current acceptance criteria.** The 300k improvement (main p50 49.6 s to branch 88 ms) is compelling, and the failure is honestly disclosed. It is still a failed binding gate, not permission to silently relax it. I recommend **option 1, immutable doc_id on search rows**, as the next measured implementation change: it removes per-chunk enumeration/large eligible arrays from common document filters, preserves authority confirmation, and introduces no ingestion identity boundary. Do not copy visibility. Measure the resulting plans and full public operations before claiming the budget passes. This option alone does not explain or fix unfiltered p95 2.3 s, so a remaining unfiltered failure needs its own measured fix or an explicit reviewed owner amendment too. The distinct-text proposal needs its own evidence/adoption decision and is not required by this review. A consciously approved, size/stratum-specific latency budget is also a legitimate option; merely labeling the failed gate “owner pending” is not that decision.

**Owner invariant.** No D142 change to chunking, reuse keys, extraction/Claimify/embedding input construction, text-origin selection or carry-forward was found. Vector validation changes write acceptance, not paid-work identity. The new test is useful and non-vacuous, and D142 now accurately admits that Claimify can rerun beyond the edit. Its “per input” proof claim remains broader than its instrumentation, and a strict xfail by itself does not bound the known gap. The requirement remains binding; this is not a demand to solve pre-existing Claimify or packing gaps in D142.

WP-RS.0, the paid LoCoMo run and the unchosen distinct-text index are explicitly excluded from findings about missing work.

## P1

1. **Sandbox fact nomination and confirmation still use different authority instants.** src/rememberstack/surfaces/query_sandbox/bridge.py:768; src/rememberstack/surfaces/query_sandbox/nomination.py:350, 436.

   _shared_snapshot exports transaction now(), but semantic_facts explicitly overrides the adapter's pinned instant with datetime.now(UTC). Confirmation then selects facts_current, whose definition uses statement_timestamp() (p9_30_0051_mutable_fact_windows.py:267), while pg_confirmed_at reports transaction now(). A predeclared validity boundary crossed during embedding/nomination can therefore remove the ranked prefix or make two SRFs answer different instants, without any concurrent write. REPEATABLE READ does not prevent it. This is the same unclosed P1-4 behavior, not just inaccurate telemetry.

   **Fix:** carry the exported authority instant into the bridge settings and every fact nomination; confirm through explicit fact-time/authority predicates at that instant, and make current facts used by the request consistent with the stated request-clock contract. Add a real bridge test crossing an already-declared boundary with two SRFs and assert the row eligibility and reported instant, not only snapshot visibility.

2. **The sandbox request deadline still fails to bound fact/entity searches and outer SQL.** src/rememberstack/adapters/postgres_p1.py:1506, 1786, 1848; src/rememberstack/surfaces/query_sandbox/bridge.py:767, 779; src/rememberstack/surfaces/query_sandbox/executor.py:700.

   Fact and entity entry points leave deadline=None instead of calling _deadline(). Their sandbox nominators supply no deadline, so the loops receive None even inside an imported ReadOperation. Reproduced both loop arguments as None under a context with a finite deadline. Pool checkout sets a statement timeout once, but successive FETCH/confirmation statements can each spend that old remaining duration; the loop's elapsed-deadline check is disabled. The exporting connection likewise keeps its original full statement_timeout for bridge confirmation and the final SQL statement. Work near the end of the budget can thus start another full-budget statement.

   **Fix:** derive every adapter call's effective deadline from ReadOperation, using the minimum when an explicit deadline is supplied. Re-clamp before actual statements/fetches and before bridge confirmation/final SQL on the exporter, or install a correctly handled whole-operation guard. Standalone facts must use that same deadline. Test elapsed time during real FETCH and confirmation, plus an SRF consuming most of the request budget before a costly outer statement.

3. **Real timeout errors can escape as database failures or be overwritten during planner cleanup.** src/rememberstack/adapters/postgres_p1.py:2006; src/rememberstack/adapters/p1_ranked.py:278; src/rememberstack/surfaces/query_engine.py:1050, 1999, 2174, 4430.

   _configure_p1_connection sets statement_timeout and transaction_timeout to the same duration. PostgreSQL can terminate the session with SQLSTATE **25P04**; _deadline_expired recognizes only **57014**, so search_claims/search_chunks/context re-raise it. Reproduced that classification with psycopg.errors.TransactionTimeout. PostgreSQL documents that an equal/shorter transaction timeout supersedes statement_timeout. Separately, a canceled EXPLAIN/DECLARE aborts the transaction, then the unconditional set_config restoration executes in that failed transaction and replaces the original error with 25P02. Standalone facts_context and nominate_claims/nominate_chunks have no matching timeout-to-envelope handling at all. [PostgreSQL timeout behavior](https://www.postgresql.org/docs/19/runtime-config-client.html), [SQLSTATE definitions](https://www.postgresql.org/docs/19/errcodes-appendix.html).

   **Fix:** normalize expected budget exceptions at every public operation boundary, including transaction termination, and preserve the original exception through cleanup. Skip SQL restoration in an aborted/disconnected transaction, relying on rollback there; restore captured values on healthy paths. Add actual SQL timeout cases during attestation, FETCH and confirmation and assert the public typed outcome. The clock-mocked between-fetch test cannot exercise these paths.

4. **Accounts are still lost at entity resolution and the final compound fact envelope.** src/rememberstack/surfaces/query_engine.py:731, 1606, 3924.

   resolve's T3 entity search ignores search_account: an empty ANN_SCAN_BOUND result produces unknown_entity with no truncation. Reproduced through the public resolve method. Nonempty capped results lose the incomplete marker too. This path also bypasses _operation and hydrates on another engine connection. In default_facts_context with anchors, the final Truncation constructor drops fact_truncation.reason; a nonempty p1_work_budget fact result becomes truncated=true, reason=None. Reproduced through the actual compound body.

   **Fix:** run the ranked resolution path and its confirmation/context reads in one operation, preserve its account, and return a boundary for a capped empty resolution. Copy/merge the fact stop reason when constructing the compound truncation. Add public empty/partial ANN-resolution and anchored default-fact-context tests. The current five account tests do not cover these consumers.

5. **Survivor-eligible facts can bypass the new entity input-row budget.** src/rememberstack/adapters/postgres_p1.py:1419, 1487.

   search_facts_scored checks the scope budget on indexed.subject_entity_id/object_entity_id directly against requested survivor IDs. Its subsequent exact query filters fact.subject_entity_id/object_entity_id from facts_visible_history, which resolves redirects. If A merged into B and 100,000 facts retain A as their stored endpoint, requesting B can count zero input rows, then score all 100,000 eligible facts. Merges update entity redirects, not every fact endpoint (clustering.py:1019). The nominate_facts_scored branch already expands the survivor scope correctly; this branch does not. Predicate-filtered facts_context uses this path.

   **Fix:** share the survivor-expanded endpoint input relation between both guards and the scoring scope, under the same snapshot. Count at most budget+1 distinct fact rows across both branches before scoring. Add a hub fixture whose raw endpoints are absorbed entities and assert entity_scope_too_broad, including through predicate-filtered facts_context.

6. **The binding latency gate remains failed.** plan/designs/postgres_p1_search_projection_design.md:593; plan/analysis/index_driven_ranked_search.md:545, 559; plan/plans/index_driven_ranked_search.md:25.

   The measured public p95 is 2,330 ms unfiltered and 3,071 ms at 1%, versus approximately 300 ms; even the filtered adapter p95 is 827 ms. The 4,990-row exact tier is also slow, and unfiltered current has a work-budget stop. These are common strata. A large improvement over main does not satisfy the declared acceptance condition.

   **Fix before merge:** implement and measure the immutable-doc_id filtering option recommended above, plus resolve any remaining common-stratum failure, or obtain an explicit reviewed owner amendment to the latency/completeness acceptance criteria and reconcile the binding corpus. Rerun on hydratable public results. This finding does not require the occupied deployment, a paid run or adoption of the distinct-text proposal.

## P2

1. **The numerical proof assumes a false token-count bound and an insufficiently restricted reciprocal-error bound.** src/rememberstack/adapters/p1_ranked.py:70, 80, 97; plan/designs/postgres_p1_search_projection_design.md:419; src/tests/adapters/test_p1_ranked.py:300.

   PostgreSQL's default parser emits overlapping compound tokens and their components: under simple, a-b contributes a, a-b and b, exceeding floor((len+1)/2)=2. The new parser test only asserts the Python formula; it never invokes the analyzer. Also, proving |error|≤gamma and epsilon≥gamma does not establish 1/(1−gamma)≤1+epsilon throughout the accepted (n+16)u≤1/2 domain. At a=0.4, the latter quantities are 3 and about 1.8. This identifies a hole in the written universal derivation, not a demonstrated wrong answer: the additional slack and PostgreSQL's own representational limits may protect realizable queries, but those limits are not the proof currently implemented/documented. [PostgreSQL parser contract](https://www.postgresql.org/docs/19/textsearch-parsers.html).

   **Fix:** use an actual analyzed-term count or a valid conservative bound; derive the score ratios with explicit denominators, or enforce and explain a sufficiently small domain at every entry point. Account explicitly for the pinned scorer's casts, positive arithmetic and float8 standalone accumulation. Add real-parser cases and boundary-domain tests; retain the successful 40,000-term counterexample and spill-mixed gate.

2. **The LoCoMo replacement loader no longer establishes per-run integrity.** benchmarks/p1_ranked/locomo_gate.py:84, 94; src/tests/benchmarks/test_p1_ranked_gate.py:53.

   load_export checks manifest/document hashes and judge presence, but not the saved configuration's own fingerprint, state/config identity, answer completeness or judge key/item_id correspondence. The new “old fingerprint” fixture actually has judges and no answers, and changes surface_manifest_hash without recomputing the run fingerprint; the loader accepts it. Those are states the runner's _validate_state/_validate_run correctly reject. A copied or mismatched state can now be scored as a finished, integrity-checked run.

   **Fix:** separate validation against each run's recorded identity from validation against current protocol pins. Reuse the former checks, require terminal answers and consistent judges for the exact manifest, and validate recorded input/ingest identities without querying a deployment. Construct a genuinely valid old-identity fixture; add missing-answer, mismatched-state/fingerprint and mismatched-judge-ID tests. This is a harness defect, not a request to run LoCoMo.

3. **Coverage tiers reset the per-search candidate work budget.** src/rememberstack/adapters/postgres_p1.py:2471, 2500.

Reproduced the accounting; this is possible with two >5,000-member tiers below the mention budget when authority rejects their members. Returned limits omit the loop budget and HNSW limits as well.

Test multiple tiers with authority rejection and verify that aggregate work respects the declared per-search cap.

4. **The sweep still does not measure the claimed production work/public-result gate.** benchmarks/p1_ranked/sweep.py:298, 361; plan/analysis/index_driven_ranked_search.md:553.

Label the existing archive diagnostic, correct the corpus-independent latency claim, and keep unswept channel/target gates explicitly incomplete.

5. **The ingestion regression is non-vacuous but still weaker than the claimed per-stage input proof.** src/tests/workers/test_reuse_lifecycle.py:706, 736, 770, 818, 837; decisions.md:6984.

6. **Python nonzero validation can still store a zero float4 vector.** src/rememberstack/ports/p1_index.py:36; src/rememberstack/spine/profile_refresher.py:726; src/rememberstack/adapters/postgres_p1.py:2229.

   require_p1_vector((1e-50,)*1536) succeeds, but every component rounds to float4 zero. The pinned pgvector input code uses strtof and permits underflow to zero, so this writes an unreachable vector despite the new contract. Reproduced the validator success and float32 conversion locally. The count exclusion avoids spurious exhaustion totals but does not reject the new invalid write. [pgvector 0.8.6 vector input](https://github.com/pgvector/pgvector/blob/v0.8.6/src/vector.c#L211-L227).

   Existing zero vectors also remain eligible in _testimony_query (postgres_p1.py:867). _exact_testimony orders 1−cosine_distance DESC (postgres_p1.py:2404): a zero vector produces NaN, which PostgreSQL sorts ahead of finite scores in descending order. Thus a legacy zero vector can displace a valid neighbor in the new exact tier, although HNSW omits it. Merely excluding it from the exhaustion count does not make the tiers equivalent. This is source/SQL reasoning, not a database reproduction. [PostgreSQL floating-point ordering](https://www.postgresql.org/docs/19/datatype-numeric.html#DATATYPE-FLOAT).

   **Fix:** validate finiteness and nonzero norm after float4 conversion, including finite Python values that overflow float4, before opening the vector write transaction. Exclude legacy zero-norm vectors consistently from exact eligibility as well as HNSW counts, with repair through the existing disposable-projection path. Add underflow/overflow writer tests and an exact-tier versus HNSW case containing an attested zero vector. This requires no change to embedding input/reuse identities.

The PR discloses this alternative, but the current-state design has not adopted/explained it; a cold reader is instructed to implement different behavior.
